## Overview

After Phase 11 the manager installs, updates and removes one plugin at a time (`commands.rs:110-224`, each command
building one `vec![action]` batch, `install.rs:4102-4113`, `:4229-4240`) and updates itself, but it cannot update every
outdated plugin behind one confirmation and one elevation prompt, it has no settings screen over the Phase 4 settings
model (no `settings_*` command exists, `lib.rs:112-123`), the stored Linux graphics toggle is read by nothing
(`linux_graphics_workaround` appears only in `settings.rs` and tests), a Linux install manifest whose plugin left the
feed cannot be removed (Phase 9 FR-094 step 1, `install.rs:4180-4184`), no first-launch documentation exists, and the
landing page has no Krate Manager card (`release.yml:823-836` renders plugin cards only).

Phase 12 completes the v1 product and proves it ready for its first public release:

1. **Update all** (Q7): one in-page confirmation listing every update; bounded parallel downloads; then one driver run per
   batch, so Windows and macOS raise exactly one elevation prompt; installers run one at a time; a locked plug-in fails
   with "close your DAW and retry" while the rest continue; every install ends with the rescan notice.
2. **The settings screen** (Linux only): the Linux plug-in root, refused while any install manifest exists, and the
   NVIDIA / WebKitGTK workaround toggle, which takes effect at the next launch and is never shipped on by default.
3. **Orphan-manifest Remove** (Linux): a plugin with a manifest but no feed entry is listed and removable from its
   manifest alone.
4. **User-performed checks** on real machines (the macOS GUI pkg install from a browser download on Sequoia and Tahoe,
   the real UAC and osascript prompts, the DAW-locked case, a Linux unprivileged install), recorded in this directory
   before the release; the macOS self-update of a pkg-installed manager, which needs two public releases, is recorded
   after the second one (D17).
5. **First-launch documentation**, written from those records, published in `apps/krate-manager/README.md` and in a
   landing-page Krate Manager card that is regenerated by every plugin release and every manager release (FR-085).
6. **Release readiness for manager 0.1.0**: every Part B gate green on Windows, every PENDING-CI row of Phases 1-11
   closed by a named green run except the enumerated post-release rows (D17), the Phase 2 backfill run live, and the
   RustSec check of the `rquickjs` crates recorded and enforced at every dispatch (FR-102, FR-104).

## Decisions taken in this spec

- **D1, "Update all" means every update the status screen offers, nothing else.** The control lists exactly the cards
  whose `PluginView.actions` contain `update` (`status.rs:73`, the output of `allowed_actions`, `install.rs:3810-3837`),
  in status order. Install for not-installed plugins and Remove are not part of it (roadmap line 899 and Q7 name updates).
  The webview sends `items: [{ name, expectedVersion }]`, exactly the versions it showed; the core never takes a URL, a
  path or an action word from the batch (the Phase 7 D9 rule, `specs/krate-manager-phase7/spec.md:260-263`).
- **D2, two stages, one driver run on Windows and macOS.** Stage 1 (check): one `feed::check` for the whole batch, then
  per item the Phase 9 FR-090 steps 2-4 against that one feed (request, install facts, busy key, destinations, driver,
  detection, gate, `allowed_actions`, refusal table). Stage 2 (obtain): bounded parallel `download::obtain_and(…, |a| a)`
  for the accepted items. Stage 3 (install): after every download has settled, Windows and macOS call
  `driver.run(env, batch)` **once** with one `Action::Update` per verified artifact, in item order, so `run_elevated`
  writes one job and launches the helper once (`install.rs:1202-1207`); Linux has no elevation, so the batch calls
  `LinuxDriver::run` once per verified action, in item order, on the same thread, which is what a single Linux batch run
  does (`install.rs:440-474`) with the item name known for each progress event. No install begins before stage 2 ends.
- **D3, the bound is three downloads at a time.** `install::BatchPolicy { parallel_downloads: usize }`, production 3;
  tests inject other values. Three keeps nine assets (today's roster) to three waves and bounds the per-attempt deadline
  exposure; it is a constant, not a setting.
- **D4, one item never stops the batch.** An item refused in stage 1 or failed in stage 2 is reported with its code and
  left out of stage 3; an item whose installer reports locked is `E_INSTALL_LOCKED` and the next op still runs (the
  helper's per-op result file, Phase 10, roadmap lines 718-720). Zero verified items: no driver run, no job, no prompt.
- **D5, exclusion.** The batch holds every accepted item's `(state_dir, stem)` busy key from stage 1 to the end of stage 3,
  so a single-card action or a second batch on any of them is `E_INSTALL_BUSY`. The page disables every action button and
  the Update-all control while a batch runs, as it does for one action (`status.ts:587-592`).
- **D6, artifacts.** A successfully updated item's artifact is `discard`ed after stage 3 (as `install.rs:4125` does); a
  failed item's verified artifact stays in staging, so a retry re-verifies it from disk without the network
  (`download.rs:1433-1443`). The batch's one feed is the feed every `obtain_and` prunes against, so no download of the
  batch prunes another item's artifact (Phase 7 FR-005: the prune keeps hashes the feed still offers).
- **D7, progress and outcome.** One `Channel<BatchProgress>`; `BatchProgress::Item { name, event: InstallProgress }` and
  `BatchProgress::Elevating` (once, from the elevated run, which emits `InstallProgress::Elevating` with no name,
  `install.rs:1353`). The command returns `BatchSummary { results: Vec<BatchItemResult>, notice: Option<Notice> }`, one
  result per requested item in request order, each `Ok(ActionSummary)` or the error text whose code comes first; `notice`
  is `RescanDawMacos` on macOS and `RescanDaw` elsewhere when at least one item updated, else `None`.
- **D8, the settings screen is Linux-only and has no folder picker.** On Windows and macOS the model holds nothing the user
  can change (no install scope, Q3; `fold` ignores the root there, `context.rs:145-153`), so no Settings control is
  rendered. The root is a text field validated by `settings::validate`, plus "Use default (`~/.vst3`)", which stores
  `null` (the `linux_plugin_root_or_default` rule, `settings.rs:27-32`). No `tauri-plugin-dialog`.
- **D9, the graphics toggle sets one variable, at the next launch, before any thread.** When the stored
  `linux_graphics_workaround` is `true` on Linux, `run()` sets `WEBKIT_DISABLE_DMABUF_RENDERER=1`: rung 3 of the Tauri
  ladder and the page's own snippet (External facts). Rungs 1 and 2 are a kernel parameter and an NVIDIA-driver variable
  the docs order before it; rung 4 is the "last resort". The toggle off sets nothing and removes nothing, so a variable
  the user exported in a shell still works. It is applied at the start of `run()`: right after `Roots::from_os()`
  (`lib.rs:46`) `run()` calls `platform::apply_graphics_env(os, settings, set)` once, before `proxy_env::read()`
  (`lib.rs:58`). `settings` is `settings::load(&roots).settings` (read-only, `settings.rs:133-153`) when `roots` is
  `Ok`; when `Roots::from_os()` is `Err`, or `load` reports an error (its `settings` are then the defaults, toggle
  `false`, `settings.rs:146-150`), no variable is set. `set` is the closure holding the one `set_var` call, in an
  `unsafe` block whose one-line reason is "single-threaded: before the first thread (sysproxy.rs:210 can spawn one from
  :61)". A change on the screen therefore takes effect at the next launch, and the screen says so.
- **D10, orphan Remove rides on `remove_plugin`.** No new command: when `name` is absent from the snapshot and the OS is
  Linux, `command_remove` looks for a manifest in `<state>/manifests/` whose `plugin` equals `name` and, if exactly one is
  found, removes from it alone (FR-050 to FR-051). The status view lists such manifests as `orphans` so the page can
  offer Remove.
- **D11, the user-performed checks are records in this directory, gated like Phase 10's M-1.** `specs/krate-manager-phase12/user-checks.md`

## Functional Requirements

### A. Update all: core (roadmap lines 899-903, 937-942; Q7)

- **FR-001** `install::batch_for_command(env: CommandEnv<'_>, staging: &(dyn StagingIo + Sync), policy: &BatchPolicy,
  items: &[BatchItem], now_unix, host: &dyn HostFacts, progress: &mut dyn FnMut(BatchProgress)) -> Result<BatchSummary,
  InstallError>` (`staging`: FR-008), with
  `BatchItem { name: String, expected_version: String }`. `BatchPolicy::PRODUCTION.parallel_downloads == 3` (D3).
- **FR-002** Input checks before any request: `items` non-empty, at most 32 entries, no name twice; else
  `E_INSTALL_BATCH { reason }` and nothing else happens (no feed request, no busy key). The cap is
  `install::MAX_BATCH_ITEMS = install::job::MAX_OPS`, a core constant 32 equal to the helper's `MAX_OPS`
  (`crates/helper/src/job.rs:11`, which refuses a larger job at `:162`, after the prompt was accepted), pinned equal by
  the cross-crate test `job::tests::core_and_helper_op_caps_agree`, so 33 items are refused before any prompt (plan SI-2).
- **FR-003** No URL, path or action word is accepted from the webview; every item is an update (D1).
- **FR-004** The first check is `self_update::action_gate(state_dir)` (`self_update.rs:402-408`), never
  `install::action_gate`: `E_INSTALL_SELF_UPDATING` refuses the whole batch.
- **FR-005** Stage 1: exactly one `feed::check(ctx, FetchMode::Normal, now_unix)` per batch (no snapshot →
  `E_INSTALL_NO_FEED` for the batch). Per item, in order, the Phase 9 FR-090 steps 2-4 with the action fixed to update
  and the batch's feed: `request_for_platform` (`expected_version` compared with the entry's `version_text`), install
  facts (`E_INSTALL_NOT_MANAGEABLE`), the busy key (`E_INSTALL_BUSY`), `Destinations::of`, `driver_for`
  (`E_INSTALL_NO_DRIVER` for the batch), detection, `install::action_gate` (`install.rs:3710`, the per-item detection
  gate), `allowed_actions` and the refusal table
  (`E_INSTALL_STATE_CHANGED`, `E_INSTALL_NOT_NEWER`). A refused item is a result, never a batch error. The single-item
  path and the batch call one shared function for these steps, so the two cannot disagree.
- **FR-006** Stage 1 makes no asset request and no mutating `InstallIo` or `StagingIo` call.
- **FR-007** Every accepted item's busy key is held until `batch_for_command` returns (D5).
- **FR-008** Stage 2: the accepted items are downloaded through `download::obtain_and(…, |artifact| artifact)` with at
  most `policy.parallel_downloads` transfers at once (`std::thread::scope`). Each worker builds its own `DownloadEnv`
  (`download.rs:204-215`) from the **injected** parts: `env.download`'s `ctx`, `policy` and `cancel`, and as its `io`
  the batch's `staging` parameter; the batch path uses `staging` for every staging call (the workers' `io` and the
  stage-3 `discard` alike) and never `env.download.io` (plan SI-11, PD-4); no worker names `FsStagingIo` or any other
  concrete staging type. Because `StagingIo` has no `Sync` bound
  (`download.rs:552`), the batch path takes its staging seam as `&(dyn StagingIo + Sync)`: `batch_for_command` receives
  it as a separate parameter `staging: &(dyn StagingIo + Sync)` (production passes `&FsStagingIo`, a unit struct; tests
  pass `FaultyStagingIo`, whose state is `Arc` of atomics, `test_support.rs:667-704`), and the single-item
  `CommandEnv.download` is unchanged (FR-019). With two or more items and a bound of two or more, transfers overlap.
- **FR-009** A failed `obtain_and` (any `E_DOWNLOAD_*`, including a verify failure) makes that item's result its error;
  the others continue (D4). Nothing unverified reaches stage 3: stage 3 accepts only `VerifiedArtifact`s, which only
  verification makes (`install.rs:292-309`).
- **FR-010** Stage 3 starts only after every stage-2 worker has returned. Windows and macOS: exactly one
  `driver.run(InstallEnv { … }, batch)` with one `Action::Update` per verified item in item order (D2). Linux: one
  `LinuxDriver` run per verified item, in item order, each with a one-action batch. No two installs run at once.
- **FR-011** Zero verified items: no driver run, so no job file, no launch.
- **FR-012** Windows and macOS: the whole batch reaches the helper as one job and one launch (`run_elevated`,
  `install.rs:1166-1263`, unchanged); one refusal at the prompt (`E_INSTALL_REFUSED`) is every stage-3 item's result and
  changes nothing on disk.
- **FR-013** An `E_INSTALL_ELEVATION_BUSY` (Phase 10 FR-078a) is every stage-3 item's result.
- **FR-014** On macOS the registrar kill runs once per batch when at least one install reported done
  (`install.rs:1215-1221`, unchanged).
- **FR-015** An item whose op reports locked has result `E_INSTALL_LOCKED: A plug-in file is in use. Close your DAW and
  retry.`; the following ops of the batch still run (Phase 10 per-op results).
- **FR-016** `BatchSummary.notice` follows D7. Each successful item's `ActionSummary` has the same `notice` as the single
  command would give it (`install.rs:4128-4133`).
- **FR-017** Progress per D7: every stage-2 event of an item is `Item { name, event: Download { event } }`; every Linux
  stage-3 event is `Item { name, event }`; the elevated run's `Elevating` is `BatchProgress::Elevating`, once.
- **FR-018** No code path in `crates/core`, `crates/helper` or `src-tauri` enumerates, detects, closes or kills a process
  other than its own children, except `platform::KILLALL_ARGV` (`platform/mod.rs:19`). Windows installers keep
  `/NOCLOSEAPPLICATIONS` (Phase 10, unchanged).
- **FR-019** `install_plugin`, `remove_plugin` and `download_plugin` keep their parameters, results and behaviour.
- **FR-020** One log line per item result (the Phase 9 FR-117 format, `install.rs:4256-4299`) and one line per batch:
  `batch of <n>: <accepted> accepted, <verified> verified, <ok> updated`. No path, URL or hash in either. On Windows and
  macOS the elevated driver's existing `elevated batch of <n> op(s): launch …` line (`install.rs:1364`) also appears,
  exactly once per batch, besides these lines (plan SI-12).

### C. Settings screen (roadmap lines 904-906; Q3; Phase 9 FR-064, FR-123 (b))

- **FR-040** `settings::view(ctx, settings_error) -> SettingsView { os, linux_plugin_root: String, root_is_default: bool,
  graphics_workaround: bool, root_locked_by: Vec<String>, error: Option<String> }`: the effective root as text, whether
  it is the default, the stored toggle, the plugins whose manifests or journals lock the root (FR-041), and the startup
  `settings_error` code text if any (`context.rs:69-70`). `SettingsError` is not `Clone` (`settings.rs:61`), so `error`
  is that error's `Display` text, read under the state guard (plan SI-17).
- **FR-041** A root change is refused with `E_SETTINGS_ROOT_IN_USE { names }` while `<state>/manifests/` holds any
  regular `*.json` file or `<state>/journal/` holds any regular `*.json` file; `names` are the manifests' `plugin` values
  (a manifest that fails to parse is named by its stem). The message tells the user to remove those plugins first. Only
  the root is locked: the toggle can always be saved.
- **FR-042** A save is refused with `E_SETTINGS_BUSY` while `install::any_busy`, `download::any_in_flight` or
  `self_update::action_gate(state_dir)` (never `install::action_gate`) say something is running; off Linux every save is
  `E_SETTINGS_UNSUPPORTED_OS`. A save is also `E_SETTINGS_BUSY` while a plugin command holds a `RootTicket` of the
  per-state-dir root gate: `install_plugin`, `remove_plugin` and `update_all` take their context through
  `settings::command_context`, which waits out a running save before cloning the context and holds the ticket until the
  core call returns, so no plugin command writes into a root a concurrent save replaced (plan SI-21, PD-11). With no
  startup context (`AppState.context` an `Err`), the view and the save return that startup error, whose text begins with
  its `E_STARTUP_*` code (plan SI-15, PD-10).
- **FR-043** `pub(crate) settings::save_for_command_with_os(os: Os, state: &SharedState, root: Option<String>,
  graphics_workaround: bool) -> Result<SettingsView, SettingsCommandError>`: the checks of FR-041 and FR-042 for `os`
  (the root check only when the root changes, compared as stored values), `settings::validate`, `settings::save`
  (atomic, refuses over a newer file: `E_SETTINGS_FUTURE_VERSION`), then `pub(crate) context::apply_settings_with_os(os,
  state, settings)`, which is `apply_settings` (`context.rs:196-204`) calling `reassemble_with_os(os, …)`
  (`context.rs:164`) instead of `reassemble` (which hard-codes `NativePlatform.os()`, `context.rs:156-158`). Likewise
  `pub(crate) settings::view_with_os(os, …)` backs FR-040. The public `save_for_command`, `view` and `apply_settings`
  are `NativePlatform.os()` wrappers over them, so the production path is unchanged and tests force any OS. A refused or
  failed save leaves the file and the running context unchanged. `apply_settings_with_os` takes the state's **write**
  guard once and reassembles and assigns under it, so no reassembled lock clone outlives the guard and
  `release_for_restart` (which takes the same write guard) never sees a second lock clone because of a save (Phase 11
  R-9; plan SI-8 (a), PD-9).
- **FR-044** Error texts begin with their codes: `E_SETTINGS_ROOT_IN_USE`, `E_SETTINGS_BUSY`, `E_SETTINGS_UNSUPPORTED_OS`

## Safety

- **Injected roots.** Every new core path (batch, settings save, orphan Remove, status orphans) reads roots only from the
  `AppContext` (`Roots`, the state dir, the configured Linux root), which tests build with `temp_roots()`. The feed URL
  and HTTP client come from `AppContext`; the elevation launcher from `CommandEnv`. `Roots::from_os()` stays the one
  production constructor (clippy `disallowed_methods`).
- **Verify before execute.** The batch hands the driver only `VerifiedArtifact`s from `obtain_and` (size, SHA-256,
  minisign signature, C3 trusted-comment binding to plugin, version, platform and asset, Phase 7); the helper re-hashes
  as it copies into its admin-only directory before it runs anything (Phase 10). Nothing is extracted on Windows or
  macOS; Linux extraction keeps Phase 8's path checks.
- **The helper.** Unchanged fixed op set (`run_inno_installer`, `run_inno_uninstaller`, `run_pkg_installer`,
  `uninstall_pkg`), compiled-in roots; the batch only puts more `run_*_installer` ops in one job. No new op, field or
  argument.
- **The webview.** Three new commands of the app's own, taking only names, versions, an optional root string and a
  boolean; no URL, path, action word or shell string; no new plugin or permission; CSP unchanged.
- **The environment.** One `set_var` of one fixed name and value, Linux only, opt-in, before any thread (D9).
- **Orphan Remove** acts only on a manifest the manager wrote, only under the configured roots (`roots_match`,
  `resolve_entries`), never on user presets or unplaced files.
- **Tests never touch** a real VST3 / Components / preset folder, ProgramData, the registry, the real helper elevated,
  an installer, github.com or api.github.com. The user-performed checks (FR-073 to FR-075) are the only real-system runs,
  performed by the user on their machines; no agent or gate runs them.
