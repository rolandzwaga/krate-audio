DESIGN NOTES / DEVIATIONS (surfaced)
1. Bend range: VoiceEngineEventKind has no bend-range event and the helpers header is read-only after T009, so
   SC-034 (range 12) and the top-note case (range 24) use veRenderWithBendRange, a TU-local copy of voiceEngineRender
   (helpers :369-427) that also calls setPitchBendRange before prepare. Same allocation, observer, issue and split
   rules; it reads back pitchBendRange() bitwise.
2. SC-019(b) is checked over every rendering voice, not only where one voice sounds: the expected Sum is -0 plus each
   rendering voice's (c * ga) * gd + (a * ga) * gd in voice-index order (the engine fill and the voice's add), with
   "rendering" read from each voice's chunk records. The single-voice samples (the stolen voice alone after the others
   release) are counted and required (> 0.3 s). Renders: MONO E1 + overlapping A1 (an audible Reset restart: a dip)
   and POLY 4 with a fifth note stealing the oldest voice (VoiceReuse: a dip), each at g = 0, 0.5, 1; plus the MONO
   render with endpoint A replaced at 0.5 s (g steps 0 -> 1 inside one interval). (d) reads the ramp from that render.
3. SC-020 events sit on grid points, so the reference applies them at the same grid point without modelling the
   latch. The reference builds its own MonoHandler / NoteProcessor / DropEnvelope / DropPhaseLock in the engine's and
   the voice's call order, resolves each note with NoteMemory::resolve and places the overlapped E2's trigger at its
   grid point + a test-side RetriggerDeclick's samplesUntilSwitch() (the voice's switch sample). MONO: E1, E2 overlapping
   at 0.1 s with a 200 ms glide, so the Drop retriggers at the dip's switch sample; the bend ramp 0 -> +1 -> -1 runs
   0.12 ... 0.32 s, during the E2 Drop. POLY: E1 / A1 / E2 / C3 staggered by 30 ms (the reference track is matched to
   the voice whose first chunk starts at that note's sample). All four Anchor modes in MONO and POLY; the f_res tap is
   gated too. Positive controls run in MONO.
4. SC-033 states: the task names a bisection on Fold amount, then excitation asymmetry. The A_s core is a sine
   (kSineAnchor), so neither knob is certain to produce an h2 (a symmetric fold of a sine adds odd harmonics; the
   excitation's effect at E1 is unread). veFindRectStates scans each knob (9 points) in the task's order and bisects
   inside the first bracketing pair; recipe.depth (sine -> 1/n, h2/h1 from about -inf to -6 dB) is a third, fallback
   knob so the states exist. The case prints which knob placed each state and the scans. The h2/h1 reading is single
   DFT bins at f and 2f (f = the core pitch tap) over the last 8 periods of the Character tap mid, with Character Amount
   0 (the stage's bypass copy, so the tap is the Fold output the meter reads).
5. SC-033 flag reads: "from either previous flag value" = each of -30 / -25 / -15 / -10 reached from the -30 state
   (flag true) and from the -10 state (flag false), by replacing endpoint A at 0.4 s; the handed flag (the halfWave
   tap) is read over the last 4 periods of each segment. Hysteresis: -20 dB reached from -25 and from -15, flag read
   over the whole 0.6 s after the switch (>= 20 E1 periods), required constant.
6. SC-033 phase sync: MONO E1, A1 overlapping at 0.3 s, A1 off at 0.5 s (ReturnToHeld), E1 off at 0.7 s, E2 at 1.2 s
   (FromSilence), under Retrigger Reset and Continue. Expected SyncPhase samples: Reset {0, 0.3 s + 71, 0.5 s + 71,
   1.2 s}; Continue {0} (FreeRunning restarts on a sounding core never take the Reset branch). The fresh core gets the
   handed controls (the grid record's afterMotion.recipe with depth / body := the law targets), the state's
   excitation, Reset, noteOn(f) and the voice's own f_core tap as its pitch input; phases compared on the L/R mid.
7. VoiceEngine_MeterBoundedAtTopNote gates meterFreqHz == the clamp of f_core at the chunk's last 16-sample pitch
   update (T007's exact form) on every chunk, never above capHz, and == capFrequency(fs) on every chunk after 100 ms
   (the bend smoother ramps the first ms; T007 found the note's lock bump holds f_core a few cents off the cap for ~8
   chunks). The task's literal "meterFreqHz == capFrequency(fs) per chunk" would fail on those first chunks without a
   defect. The "no HalfWave call inside a period shorter than 2 samples" arm reads, for every HalfWave change handed
   after the first interval, the meter frequency of the chunk before that grid point and requires fs / f >= 2.
