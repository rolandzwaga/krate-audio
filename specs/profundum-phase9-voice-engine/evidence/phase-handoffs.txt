10.3 Latency 64 samples (G14-1, user ruling 2026-10-21; FR-025 amended): latencySamples() returns the TruePeakLimiter's
     look-ahead, kLimiterLookaheadSamples = 64 (profundum_engine.h:107, engaged at :186, read at :444; 1.33 ms at
     48 kHz, 0 before prepare). THE PHASE 10 PROCESSOR MUST REPORT IT to the host (setLatencySamples / getLatencySamples
     after setupProcessing, re-read after every prepare). The rest of the chain adds none: static_assert MassDynamics /
     BassStereoField latency 0 (profundum_engine.h:128); MassDynamics / BassCompressor / TransientShaper latency 0
     (mass_dynamics.h:735-737 static_assert "FR-014: the Mass dynamics adds no latency"). Why: the zero-look-ahead limiter
     clamps every sample to the ceiling but its per-sample gain steps overshoot between samples (+1.02 dBTP measured in the
     30 min soak); the look-ahead ramps the gain over 64 samples and the soak reads -0.95 / -0.98 dBTP against -1 dBTP + 0.1.

     oversampler). After T029 lever 2 only the compressor's sidechain (HP + held-peak detector) runs at f*fs on an
     upsampled copy; the audio, gain computer, gain application and trim stay at the base rate
     (mass_dynamics.h:700-727, processOversampled; sidechain factor set at :551). Ruling: spec.md:1118-1122 ("T005's group-delay expectation (plan
     S7 ~3.8 samples) becomes 0"). Measured: evidence/os-dynamics-delta.txt:13 "delay_base_samples 0 (peak on the
     search edge)"; neutral transfer on/off 0 dB at 40 / 200 / 1000 / 5000 Hz (os-dynamics-delta.txt:7-10); Mass 100
     steady GR off -7.1242 / on -7.12423 dB, makeup 5.8421 / 5.8421 dB (os-dynamics-delta.txt:19).
     Note for the reader: the comment at mass_dynamics.h:541-543 still says "only the gain APPLICATION is
     oversampled"; the code below it (:551, :712-725) and the spec ruling say the sidechain. The code is authoritative.
10.5 Events (C-9, plan:242-251): every event and setter is latched at the engine's current sample and applied at the
     first 32-sample grid point at or after it; the API carries NO sample offsets (profundum_engine.h:17-20). The Phase 10
     processor therefore splits each host block at every event's sample offset and issues the event before rendering
     that sample. Note queue kMaxQueuedEvents = 256 (profundum_engine.h:101): a full queue drops the note-on and counts it
     (droppedEvents(), :439); a note-off is never dropped (128 pending-release flags, :102, :275-285). Velocity 0 is a
     note-off (:259-266).
10.6 MassDynamics opt-in at 192 kHz (C-3): SUPERSEDED. Plan C-3 (plan:171-174) made the opt-in a recorded no-op at 192 kHz
     because the compressor's rate clamps at 192 kHz. Since T029 only the sidechain is oversampled and "the requested
     factor runs at every sample rate; the compressor's rate ceiling no longer binds" (mass_dynamics.h:541-545:
     osEffectiveFactor_ = requested ? osFactor_ : 0; oversamplingActive() comment :669). So at 192 kHz the opt-in is
     ACTIVE at 4x (sidechain at 768 kHz equivalent). Phase 10 has nothing to special-case at 192 kHz. The
     ProfundumEngineConfig comment at profundum_engine.h:87-89 and the mass_dynamics.h:541-544 comment were corrected at
     the close (2026-10-21): the SIDECHAIN (HP + detector) is oversampled, the gain is applied at the base rate.
     SC-021(b) reading with the opt-in: P-3 GREEN at -89.5 dBFS worst (48 kHz), bar -80 dBFS (spec.md:1122); 4x reaches
     -96.9 / -90.8 dBFS at 44.1 / 48 kHz (spec.md:1115-1117).

10.11 Low-cutoff split filters in a float chain (G14-12, user ruling 2026-10-21; for Phase 10+ and every later KrateDSP
     component): a float32 TDF2 biquad at fc / fs <= 0.01 (500 Hz at 48 .. 192 kHz) rounds its state coherently with
     a periodic input and leaves a -100 .. -118 dBFS quasi-periodic floor at the note's sample-phase beat; downstream
     HF emphasis + clipping lifted it to -65 .. -78 dBFS at Profundum's voice sum (SC-021(a), 102 of 432 cells). The
     excitation split (profundum_core.h) and the Fold split (harmonic_fold.h) now use primitives/lowpass_biquad_d.h
     (LowpassBiquadD: double coefficients and state, float interface, same RBJ design): floor -108 -> -132 dBFS at
     48 kHz, -100 -> -124 at 96 kHz; 102 -> 10 failing cells. Use it (or a TPT SVF) for any low-cutoff split in a
     chain that is measured below -90 dBFS; a Biquad there is a known floor, not aliasing. The probe chain that found
     it: profundum_engine_aliasing_test.cpp VoiceEngine_AliasingSumProbe / VoiceEngine_AliasingCoreProbe{,2,3,4}.
