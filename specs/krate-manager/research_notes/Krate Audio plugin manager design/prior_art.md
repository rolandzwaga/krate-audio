# Prior art: audio-plugin install/update managers (state as of October 2026)

Research date: 2026-10-29. Scope: how existing plugin managers (commercial and open source) are built and behave, analogous non-audio launchers, package-manager alternatives, and the UX conventions users expect. Framework attributions marked "(inferred)" rest on third-party binary scans or packaging metadata, not vendor statements. Several vendor support pages (Zendesk-hosted: Arturia, iZotope, Plugin Boutique; Native Instruments community) refused automated fetches (HTTP 403 / JS-only); for those, facts come from search-result excerpts of the cited page and are flagged.

## Key question 1: Commercial managers (framework, install mechanics, admin rights, version detection, uninstall, complaints)

### Takeaway
Most vendor managers are Electron shells (Native Access, Waves Central, Softube Central, Splice) at 350-875 MB; the exceptions are Qt (Arturia Software Center, 80 MB), JUCE (Spitfire Audio App, 86 MB) and a native app (Kilohearts Installer, 25 MB). All of them download and run vendor installer packages rather than copying files; the ones that elevate once via a privileged helper/daemon (Native Access's NTK Daemon) generate the most support traffic, and the most praised experiences (Audio Damage, Arturia, Cherry Audio Sync's design) are the ones with a single screen, visible installed-state, per-product and update-all actions, and no background service.

### Inferences
- Electron is the dominant stack for vendor managers and correlates with size: Native Access 574 MB, Waves Central 826 MB, Softube Central 875 MB, Splice 357 MB, versus Arturia (Qt) 80 MB, Spitfire (JUCE) 86 MB, Kilohearts (native) 25 MB. Waves' "250 MB updates every month" complaint is consistent with shipping a full Electron bundle per update via electron-updater.
- Every surveyed manager installs by downloading and executing the vendor's own installer package (NA deletes the installer afterwards; Toontrack and Arturia run them silently); none copies plugin bundles directly. This is why the "install for all users" case requires elevation and why NA introduced a persistent privileged daemon (NTK Daemon), which is the single largest source of NA support threads found.
- Cherry Audio Sync's "fewer password prompts" wording implies it batches elevation across several installs; its "not a background service" statement is positioned as a feature, which suggests users resent resident helpers (compare the UJAM complaint about launching at every host scan).
- Version misreporting (Sync showing updates with identical version numbers; NA "misreported updates") is a recurring failure mode; managers that show a visible installed version per product and gate "Update" on a strict comparison avoid it.
- Install-location UX splits into two models: a global preference set once (NA: Download / Application / Content locations; Cherry: custom folder + format choice; ASC: destination folders at first install) versus per-install prompting (Toontrack expansions, Spitfire per-library). Users punish hidden or unchangeable paths (NA path settings "easy to miss"; IK "can't use D:").

- Arturia and iZotope support articles and Plugin Boutique's help center returned HTTP 403; the NI community pages render only via JavaScript, so the "Dev Talks: Why We Transformed Native Access" post could not be read ([link](https://community.native-instruments.com/discussion/comment/45319)). - No manager documents how it detects installed versions (registry keys, receipts, bundle metadata); only the complaints about misdetection were found.

## Key question 2: Open-source managers, installers and scanners (language, stars, activity)

### Takeaway
No open-source project does the full job (detect installed plugins, show updates, download/install/uninstall, self-update) across Windows/macOS/Linux. The closest building blocks are PluginVault (Tauri 2 + Rust + React scanner that reads `moduleinfo.json`, `Info.plist` and PE version info; MIT; near-zero adoption), yabridge's `yabridgectl` (a CLI manager with add/status/sync semantics, 4.2k stars), and the Steinberg VST3 bundle metadata (`Contents/Resources/moduleinfo.json`) that lets a manager read name, vendor and version without loading the binary. Open-source plugin projects (Surge XT, Cardinal, Airwindows Consolidated) ship per-OS installers (Inno Setup .exe, .pkg) and leave distribution to winget/Homebrew/Flathub/distro repos.

- CLAP search paths: Linux `~/.clap`, `/usr/lib/clap`; Windows `%COMMONPROGRAMFILES%\CLAP`, `%LOCALAPPDATA%\Programs\Common\CLAP`; macOS `/Library/Audio/Plug-Ins/CLAP`, `~/Library/Audio/Plug-Ins/CLAP`; plus `CLAP_PATH` — [free-audio/clap entry.h](https://raw.githubusercontent.com/free-audio/clap/main/include/clap/entry.h)

- Cardinal (DISTRHO): GPL-3.0+, about 3.2k stars, 2,011 commits; Windows 32/64-bit and macOS Universal builds "with an installer"; Linux armhf/arm64/i686/riscv64/x86_64; nightlies via GitHub Actions (GitHub login required); "the macOS and Windows builds are unsigned, so users may see 'untrusted developer' warnings" — [GitHub: DISTRHO/Cardinal](https://github.com/DISTRHO/Cardinal)

- Heroic-style Linux packaging for an audio plugin set is shown by Arch's `dpf-plugins-vst3`, which installs each plugin as `usr/lib/vst3/<Name>.vst3/Contents/x86_64-linux/<Name>.so` — [Arch: dpf-plugins-vst3 file list](https://archlinux.org/packages/extra/x86_64/dpf-plugins-vst3/files/)
- DAW-side precedent: Ardour's Plugin Manager can "re-scan all currently known plugins, or only those that previously failed" — [Ardour manual: Plugin Manager](https://manual.ardour.org/working-with-plugins/plugin-manager/); Ardour's VST3 discovery deduplicates Windows bundle vs bare DLL — [Ardour commit 5950df2b74](https://git.ardour.org/ardour/ardour/commit/5950df2b74)

### Inferences
- The combination Krate needs is unprecedented in open source: PluginVault proves a Tauri 2 + Rust scanner that reads `moduleinfo.json`/`Info.plist`/PE version info is feasible in a few thousand lines, but it has one star and four commits, so it is study material, not a dependency. yabridgectl's `status`/`sync` CLI model (declare directories, reconcile state, re-run after changes) is a cleaner architecture reference than any GUI manager.
- Because Krate controls its own plugins, it can guarantee `moduleinfo.json` is present and populated (`name`, `version`, `factoryInfo.vendor`) in every bundle, sidestepping the version-misdetection failures reported for KSM and Pluginize, which must handle arbitrary vendors' inconsistent metadata.
- Every mature open-source plugin project (Surge, Cardinal, Airwindows) ships per-OS installers and lets third parties (winget, Homebrew, Arch, Flathub) do "management"; none has written an in-house manager, which suggests the marginal value of a manager over signed-less installers + package managers is in update visibility and uninstall, not in the install step itself.
- Cardinal's explicit "unsigned builds show untrusted-developer warnings" note is the same situation Krate is in; a manager that downloads and extracts bundles itself (rather than launching an unsigned .pkg/.exe) avoids the Gatekeeper/SmartScreen prompt for the installer but not the quarantine attribute on downloaded files, which the manager would have to clear or avoid by writing files itself.

### Gaps
- GitHub pages did not expose last-commit dates for PluginVault, vst-manager, Surge, Cardinal, airwin2rack or yabridge; activity recency is inferred from commit counts and version numbers only.
- No open-source project that checks vendor sites for newer versions was found; KSM (closed) and PlugPane (closed) are the only update-comparison implementations, both server-backed.
- KXStudio's Carla `carla-discovery` out-of-process scanner and MOD Devices' plugin store were not researched (kx.studio returned a TLS certificate error for `kx.studio`; see Key question 4 for repository facts from mirrors).
- Pluginize's maker-identification details ("the identifier a plugin carries") are developer claims from a marketing thread; the mechanism (AU manufacturer code? VST3 vendor string?) is not documented.

## Key question 3: Analogous non-audio launchers/managers (Tauri, Electron, Qt, Compose) and their download/install/self-update models

### Takeaway
Modrinth App is the proven Tauri 2 reference (Rust core + Vue 3, `tauri-plugin-updater`, SQLite), and Tauri's updater gives signed static-JSON or dynamic-endpoint updates with NSIS/MSI on Windows, `.app.tar.gz` on macOS and AppImage only on Linux. Electron launchers (Heroic, GitHub Desktop) rely on electron-updater/Squirrel, which require code-signed builds on macOS and have no Linux auto-update. Qt (Prism) and Compose Multiplatform (JetBrains Toolbox) show native-sized alternatives; Flatpak-first Linux tools (Bottles, Lutris) defer self-update to the package manager entirely.

### Cited Findings

**Modrinth App (Tauri)**
- The Modrinth App ("Theseus") uses Tauri with a Rust backend and a Vue.js frontend; three parts: a Tauri shell (`apps/app/`), a Vue 3 frontend (`apps/app-frontend/`), a Rust core library (`packages/app-lib/`); internal database is SQLite (`app.db`) — [Modrinth docs: Theseus](https://docs.modrinth.com/contributing/theseus/); [Mintlify mirror: desktop app](https://www.mintlify.com/modrinth/code/development/desktop-app)
- Monorepo `modrinth/code`: 2.5k stars, 656 forks, 5,038 commits; packages "licensed under their respective licenses" (COPYING.md) — [GitHub: modrinth/code](https://github.com/modrinth/code)
- `apps/app/Cargo.toml` depends on `tauri` (features `devtools`, `macos-private-api`, `protocol-asset`) and plugins `tauri-plugin-updater` (also declared optional under the Linux target), `tauri-plugin-http`, `tauri-plugin-fs`, `tauri-plugin-dialog`, `tauri-plugin-deep-link`, `tauri-plugin-opener`, `tauri-plugin-os`, `tauri-plugin-single-instance`, `tauri-plugin-window-state`; `hyper` (server) and `hyper-util`; the version is stamped by the `theseus-build` workflow at release — [modrinth/code apps/app/Cargo.toml](https://raw.githubusercontent.com/modrinth/code/main/apps/app/Cargo.toml)
- The 2023 beta announcement lists "an auto-updater to ensure the app is always up-to-date" — [Modrinth: App beta](https://modrinth.com/news/article/modrinth-app-beta); distributed on Flathub and AUR (`modrinth-app-git`) and winget — [Flathub](https://flathub.org/ro/apps/com.modrinth.ModrinthApp); [AUR PKGBUILD](https://aur.archlinux.org/cgit/aur.git/tree/PKGBUILD?h=modrinth-app-git); [wingetly](https://wingetly.io/apps/modrinth/modrinth-app)

**Tauri 2 updater plugin (what Modrinth and any Tauri manager inherit)**
- Updates must be signed; `tauri signer generate` creates the keypair, the public key goes in `tauri.conf.json`, the private key via `TAURI_SIGNING_PRIVATE_KEY` at build time; losing the key means no further updates to existing installs; endpoints support `{{current_version}}`, `{{target}}`, `{{arch}}`; TLS enforced in production — [Tauri docs: Updater](https://v2.tauri.app/plugin/updater/)
- Static JSON (e.g. a `latest.json` on GitHub Releases) needs `version` and per-platform (`OS-ARCH`) `url` + `signature` (signature = file contents), optional `notes`, `pub_date`; every platform entry must validate; dynamic servers return `204 No Content` when nothing is newer — same source
- Windows `installMode`: `passive` (default, progress bar, no interaction), `basicUi`, `quiet` ("the installer can't request admin rights itself, so this only works for per-user installs or when the app already runs elevated"); Windows installers force the app to exit before installing; NSIS and MSI supported; macOS produces `.app.tar.gz` + `.sig`; Linux: only AppImage is described for the updater; restart after install is optional — same source
- Rust 1.90+ required; downgrades blocked unless the version comparator is overridden — same source

**Prism Launcher (Qt/C++)**
- "Prism is built with the Qt toolkit, requiring very few system resources to run" — [prismlauncher.org](https://prismlauncher.org/); the 8.0 changelog lists "Implement updater for Windows and Linux" (Added), "Allow disabling bundling and Sparkle updater when building" (Changed) and "Only build updater when correct conditions are met" (Fixed) — [Prism Launcher 8.0 release notes](https://prismlauncher.org/news/release-8.0/); the updater is a separate Qt application compiled as a static library (`prism_updater_logic`) per a fork's CMake — [PollyMC commit](https://git.plan9.rocks/fn2006/PollyMC/commit/518962c47291af69ae3dd584bc9bc2fa5d7d2caa); packaged on Chocolatey and Arch — [Chocolatey: prismlauncher](https://community.chocolatey.org/packages/prismlauncher/7.0.0); [Arch packaging](https://gitlab.archlinux.org/archlinux/packaging/packages/prismlauncher/-/merge_requests/5)

**Heroic Games Launcher (Electron)**
- Electron + React + TypeScript, Vite, MUI, electron-builder; GPL-3.0; about 12.5k stars, 2,957 commits; backends Legendary (Epic), gogdl (GOG), Nile (Amazon); distributed as Flatpak, .deb, .rpm, AppImage, .tar.xz, AUR, Nix (Linux), installer .exe and portable .exe plus WinGet (Windows), .dmg and Homebrew cask (macOS) — [GitHub: Heroic-Games-Launcher](https://github.com/Heroic-Games-Launcher/HeroicGamesLauncher)

**JetBrains Toolbox (Kotlin + Compose Multiplatform)**

### Inferences
- Modrinth demonstrates the exact shape Krate would build: Tauri shell + Rust core library (downloads, SQLite state) + web frontend, with `tauri-plugin-updater` for self-update and `tauri-plugin-http`/`fs`/`dialog` for downloads, file placement and folder pickers. Its Linux `tauri-plugin-updater` being optional matches Tauri's AppImage-only Linux updater: Flatpak/AUR builds are updated by their package managers instead.
- Tauri's mandatory update signing (minisign-style keypair) is independent of OS code signing, so an unsigned Krate app can still ship authenticated self-updates; the trade-off is that `quiet` installs cannot elevate, so a per-user install of the manager (and per-user plugin folders) is the frictionless path on Windows.
- Electron's path (electron-updater/Squirrel) is a poor fit for Krate because macOS auto-update requires Developer ID signing, which Krate does not have, and Linux has no built-in updater.
- Bottles/Lutris show that on Linux the accepted answer to "self-update" is "do not; let Flatpak/distro handle it" — a manager should detect when it was installed by a package manager and hide its own updater, as Prism's "only build updater when correct conditions are met" implies.

### Gaps
- Modrinth's update endpoint (static `latest.json` vs dynamic server) was not confirmed; only the plugin dependency is proven.
- Prism's self-updater mechanism (file replacement, download source) is not described in the release notes; the Sparkle reference is not tied to a platform in the text.
- GitHub Desktop's use of Squirrel is inferred from Electron defaults, not from its source.
- A broader "awesome Tauri launcher" survey was not done; Modrinth is the only Tauri launcher verified.

## Key question 4: Package-manager alternatives (winget, Scoop/Chocolatey, Homebrew, Flatpak, KXStudio, AUR, Nix) and their limits for VST3/AU

### Takeaway
winget accepts unsigned installers (its policies have no code-signing clause) but requires silent install/uninstall for admins and non-admins and an installer URL on the publisher's own domain; Homebrew is closing to unsigned software (5.0.0, Nov 2025: casks without codesigning deprecated, Gatekeeper-failing casks disabled from Sept 2026, `--no-quarantine` deprecated) and its `vst3_plugin` stanza installs per-user only; Flatpak needs plugins packaged as `org.freedesktop.LinuxAudio.Plugins.*` extensions mounted at `/app/extensions/Plugins/<format>`, invisible to native hosts; Arch, Nix and Debian/KXStudio each have clear `/usr/lib/vst3` conventions but no shared mechanism for proprietary-style binary drops.

### Cited Findings

**winget (Windows Package Manager)**
- Submission expectations: manifest complies with schema; installer and app virus-free (Defender false positives can be appealed); "the application installs and uninstalls correctly for both administrators and non-administrators"; "the installer supports non-interactive modes"; "the installer comes directly from the publisher's website"; validation labels include `Validation-Unattended-Failed` (not silent), `Validation-Uninstall-Error` (incomplete cleanup), `Validation-HTTP-Error` (must be HTTPS), `Validation-Indirect-URL` (no redirectors), `Binary-Validation-Error` (AV/PUA flags across several AV engines) — [Microsoft Learn: Submit your manifest](https://learn.microsoft.com/en-us/windows/package-manager/package/repository)
- Repository policies (v1.0, 22 May 2021; page updated Aug 2026): 1.1.4 "The InstallerUrl must be the ISV's release location ... Products from download websites will not be allowed"; 1.2 Security (no dynamic code download beyond described functionality; no malware); the policy text contains no code-signing requirement — [Microsoft Learn: Windows Package Manager repository policies](https://learn.microsoft.com/en-us/windows/package-manager/package/windows-package-manager-policies)
- Manifest: `InstallerType` enumeration shown as exe, msi, msix, inno, wix, nullsoft, appx, font; "all tools must support a silent install"; Inno/Nullsoft types get silent switches automatically; `PackageName`/`Publisher` should match Add/Remove Programs for `upgrade` correlation; MSI product codes recommended — [Microsoft Learn: Create your package manifest](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest)
- A developer's CI discussion notes "Windows runs an unsigned .exe after a SmartScreen prompt, but refuses outright to install an unsigned MSIX/AppX" (anecdotal) — [getopenscreen PR #285](https://github.com/getopenscreen/openscreen/pull/285.diff)
- Surge XT is already distributed via winget with Inno Setup silent switches — [wingetly: Surge XT](https://www.wingetly.io/apps/surge-synth/surge-xt/silent-install)

**Chocolatey / Scoop**
- Chocolatey community feed: "all new versions of packages are human reviewed prior to approval"; trusted packages "only go through automated moderation review"; checks include VirusTotal validation — [Chocolatey docs: Moderation](https://docs.chocolatey.org/en-us/community-repository/moderation/); [Chocolatey docs: Security](https://docs.chocolatey.org/en-us/information/security)
- Scoop: no sources on bucket acceptance criteria for installers or plugins were found (see Gaps).

**Homebrew (macOS)**
- Cask artifact stanzas `vst_plugin`, `vst3_plugin`, `audio_unit_plugin` move the bundle into `~/Library/Audio/Plug-Ins/VST`, `~/Library/Audio/Plug-Ins/VST3`, `~/Library/Audio/Plug-Ins/Components` (per-user); `pkg` artifacts run through `/usr/sbin/installer` outside the cask sandbox and "every pkg must be accompanied by an uninstall stanza"; uninstall techniques run in fixed order (`early_script`, `launchctl`, `quit`, `signal`, `login_item`, `kext`, `script`, `pkgutil`, `delete`, `trash`, `rmdir`); `pkgutil:` is preferred, `delete:` a last resort; `zap` removes prefs/caches on `brew uninstall --zap`; `unsigned_accessibility` caveat warns users an unsigned app must be re-enabled after each update — [Homebrew: Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)
- Acceptable Casks: on macOS "apps, installers, and other executable artefacts that Gatekeeper can assess must pass Homebrew's Gatekeeper checks" and "must not require System Integrity Protection or Gatekeeper to be disabled or bypassed"; notability is judged by shared metrics with exceptions for established maintainers or verifiable public interest; betas via `@beta`/`@nightly` tokens — [Homebrew: Acceptable Casks](https://docs.brew.sh/Acceptable-Casks)

**Flatpak / Flathub (Linux)**
- Extension point `org.freedesktop.LinuxAudio.Plugins`, mounted at `/app/extensions/Plugins` with per-format subdirectories `lv2`, `ladspa`, `dssi`, `vst` (`lxvst` fallback), `vst3`, `clap`; host apps add an `add-extensions` entry (version matching the runtime, 23.08 at writing), set `merge-dirs` to the formats they support and export `VST3_PATH` (optionally with `~/.vst3`), `LV2_PATH` (must include `$HOME/.lv2`, via a wrapper script), `VST_PATH`/`LXVST_PATH`, `DSSI_PATH`, `LADSPA_PATH` — [GitHub: flathub/org.freedesktop.LinuxAudio.BaseExtension](https://github.com/flathub/org.freedesktop.LinuxAudio.BaseExtension)
- Origin (Apr-Jul 2020): proposal by Hubert Figuière; base app trimmed to a BaseExtension of extension points; unified extension point so one package ships several formats; Ardour, LMMS, Hydrogen, Muse3 adapted; plugins must be self-contained because shared libraries conflict inside one host process; Qt5/Gtk2 plugins fail silently on runtimes lacking them — [Flathub Discourse: Proposal for audio plugins](https://discourse.flathub.org/t/proposal-for-audio-plugins/399); known issues thread — [Flathub Discourse](https://discourse.flathub.org/t/issues-with-org-freedesktop-linuxaudio-baseextension/1055)
- Examples of VST3-shipping extensions: Dexed, Stochas (VST3 + CLAP), SonoBus — [pkgdex: Dexed](https://pkgdex.org/download/org.freedesktop.LinuxAudio.Plugins.Dexed); [Stochas](https://pkgdex.org/download/org.freedesktop.LinuxAudio.Plugins.Stochas); [SonoBus](https://pkgdex.org/download/org.freedesktop.LinuxAudio.Plugins.SonoBus)
- Limits: Flatpak OBS supports only Flatpak extensions, not user or system VST folders — [OBS forum](https://obsproject.com/forum/threads/flatpak-obs-cant-find-flatpak-vst-plugins.158850/); Flatpak Ardour users reach host-side plugin folders by exporting `LADSPA_PATH`, `VST3_PATH`, `LXVST_PATH` with Flatseal (LV2_PATH missing by default) — [Ardour Discourse](https://discourse.ardour.org/t/ardour7-in-flatpak-overcoming-the-sandboxing-with-flatseal/107984); plugin add-ons are hard to discover in GNOME Software — [GNOME Software issue 1020](https://gitlab.gnome.org/GNOME/gnome-software/-/issues/1020)

### Inferences
- winget is the only mainstream manager where an unsigned, free VST3 installer is acceptable today, provided the installer is silent, HTTPS-hosted on krateaudio.com (not a redirector), and uninstalls cleanly for non-admin users; the catch is that winget's "non-administrator" test implies the installer must work per-user (`%LOCALAPPDATA%\Programs\Common\VST3`), which Steinberg labels "mainly for development use" and some hosts may not scan.
- Homebrew is effectively closed to Krate's unsigned plugins from September 2026: the `vst3_plugin` stanza would place bundles per-user, but Gatekeeper-failing casks are disabled and `--no-quarantine` is deprecated; a third-party tap with `brew trust` remains possible but still cannot clear quarantine, so users would need `xattr -cr`.
- Flathub distribution only reaches Flatpak-packaged hosts (Ardour, LMMS, etc.) via the extension mount; it cannot serve native-installed DAWs (Bitwig, Reaper .deb), so a Linux manager must still write to `~/.vst3`/`/usr/lib/vst3` for most users, and conversely a Flatpak-packaged manager could not write there without broad filesystem permissions.
- Distro conventions (`/usr/lib/vst3/Name.vst3/Contents/x86_64-linux/Name.so`) are consistent across Arch, Debian and Nix, so a manager writing a standard VST3 bundle into `~/.vst3` is compatible with every Linux host without packaging work.

## Key question 5: UX conventions users expect (cards, Install/Update/Installed states, Update all, release notes, progress, restart-DAW and AU-cache notes, install location, per-user vs all-users)

### Takeaway
The conventions users reward are: one list/grid with a per-product state button (Install / Update / Installed / Reinstall / trash-uninstall), an Updates-only view plus "Update all", a visible installed version, resumable downloads with a queue, format and location chosen once in Preferences (and respected afterwards), uninstall that preserves user presets, no resident background service, and a clear post-install step ("rescan/restart your DAW"; on macOS, Logic's Plug-in Manager rescan or AU cache reset). The failure modes users name most are installing everything, no download queue, stalled downloads, forced full reinstalls, phantom updates with identical version numbers, and hidden or unchangeable paths.

### Inferences
- A Krate manager without accounts or licences can drop the Activate/Trial/Store states that dominate vendor UIs and reduce each product card to Installed version, Available version, one action button (Install / Update / Reinstall / Remove) and release notes — the Audio Damage model that the KVR thread singles out as best.
- Because Krate plugins are unsigned, the post-install notice on macOS matters more than for signed vendors: the manager should either write bundles itself (no `com.apple.quarantine` on files it creates) or clear the attribute, and should show Apple's Plug-in Manager rescan steps for AU rather than relying on `killall AudioComponentRegistrar`, whose reliability is disputed.
- The two location decisions to expose once are (a) per-user vs all-users (which also decides whether elevation is ever needed; per-user avoids the NTK-Daemon class of failure entirely but Windows per-user VST3 is labelled development-only by Steinberg) and (b) an optional custom VST3 folder for users who already point their DAW elsewhere (the IK "can't use D:" and NI relocate complaints).
- "Uninstall keeps presets" (Sync) and Homebrew's zap distinction suggest a two-level remove: Remove plugin (binaries only) and Remove everything (plus `C:\ProgramData\Krate Audio\<plugin>` / Application Support presets), with the latter opt-in.
- Download robustness (resume, queue, parallel but bounded, verified hash) is the feature most often missing in managers users call "the worst"; it should be designed in from the start rather than bolted on.
