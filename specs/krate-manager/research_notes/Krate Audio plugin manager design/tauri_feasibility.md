# Tauri 2.x feasibility for a Krate Audio plugin install manager (state as of 2026-10-29)

Scope: a Windows/macOS/Linux desktop app that lists installed plugins, polls a JSON feed, downloads GitHub Release assets with progress, verifies checksums, installs/updates/uninstalls VST3/AU bundles in admin-only folders, and updates itself. Constraint: no code-signing certificates on any OS, ever. All claims below are tagged **[documented]** (official docs or source), **[reported]** (GitHub issue/PR, forum, blog), or **[inference]** (my reasoning from the cited facts). Tauri 1.x material is marked **[legacy v1]**.

Versions seen on 2026-10-28/29 (crates.io): `tauri` 2.12.5 (2026-10-21, MSRV Rust 1.90; a `3.0.0-alpha.5` also exists) — [crates.io/tauri](https://crates.io/crates/tauri). Plugins: see Q1.

## Q1. Tauri 2 plugin ecosystem for the manager's jobs (download, fs, spawn, dialog, updater, store) — versions and maintenance in 2026

### Takeaway
Every job has a first-party `tauri-apps/plugins-workspace` plugin that was released in October 2026 (all require Rust ≥ 1.90), so maintenance is not a concern; but downloads with progress/resume and all privileged file operations are better done in Rust commands (reqwest + `std::fs`) than through the JS-facing plugins, whose scopes/limits are designed for the webview, not for a system installer.

### Cited Findings
- Plugin versions and last-update dates on crates.io (fetched 2026-10-29 via the crates.io API, all under `tauri-apps/plugins-workspace`): `tauri-plugin-updater` 2.14.1 (2026-10-28, 13.5 M downloads); `tauri-plugin-fs` 2.7.1 (2026-10-14); `tauri-plugin-shell` 2.6.0 (2026-10-28); `tauri-plugin-process` 2.4.0 (2026-10-14); `tauri-plugin-dialog` 2.8.4 (2026-10-28); `tauri-plugin-store` 2.5.0 (2026-10-14); `tauri-plugin-http` 2.8.3 (2026-10-14); `tauri-plugin-opener` 2.7.2 (2026-10-14); `tauri-plugin-os` 2.4.0; `tauri-plugin-upload` 2.5.0 (2026-09-30, only 167 k downloads); `tauri-plugin-log` 2.10.1; `tauri-plugin-single-instance` 2.5.5; `tauri-plugin-window-state` 2.5.0 — [crates.io search API](https://crates.io/api/v1/crates?q=tauri-plugin&per_page=50&sort=downloads). **[documented]**
- `tauri-plugin-http` is "available in both Rust as a reqwest re-export and JavaScript"; the JS `fetch` is a near-but-not-identical Web Fetch clone; URL access is an allow/deny list in `capabilities/default.json` (`http:default` permits no origins until configured); forbidden request headers are ignored unless the `unsafe-headers` feature is enabled; no progress/streaming API is documented on the page — [HTTP Client plugin](https://v2.tauri.app/plugin/http-client/). **[documented]**
- `tauri-plugin-upload` `download(url, filePath, progressHandler, headers, body)` saves the response body to disk and calls the progress handler per chunk with `progress` (bytes in the last chunk), `progressTotal`, `total` (from `Content-Length`, 0 if absent) and `transferSpeed`; no resume is mentioned; the parent directory must exist, an existing file is overwritten, and a failed download leaves the partial file — [Upload plugin](https://v2.tauri.app/plugin/upload/). **[documented]**
- `tauri-plugin-fs`: scopes are `{ path }` entries in allow/deny lists, deny wins, variables like `$APPDATA`, `$HOME`, `$RESOURCE`, `$TEMP`; absolute paths are allowed (Rust example `scope.allow_directory("/path/to/directory", false)`); a permission alone grants no path ("Enabling a permission such as `fs:allow-exists` by itself does not allow access to any path"); `..` is rejected; on the Rust side the plugin only manages scopes — "use `std::fs` or `tokio::fs`" for actual file work; note "On Windows, apps installed via MSI or NSIS in `perMachine` or `both` mode need admin rights to write to `$RESOURCES`" — [File System plugin](https://v2.tauri.app/plugin/file-system/). **[documented]**
- `tauri-plugin-shell`: spawns child processes and sidecars; every command exposed to JS must be allow-listed in capabilities with `name`, `cmd`, `args` (static values or `{ "validator": "<regex>" }`) and a `sidecar` flag; "By default all potentially dangerous plugin commands and scopes are blocked"; the `shell.open` API is superseded by the Opener plugin; Rust API via `app.shell().command(..).args(..).output()` — [Shell plugin](https://v2.tauri.app/plugin/shell/). **[documented]**
- Sidecars: list binaries under `bundle.externalBin` with a target-triple suffix on the file (`my-sidecar-x86_64-unknown-linux-gnu`); run via `app.shell().sidecar("my-sidecar")` or `Command.sidecar(...)` in JS; permissions `shell:allow-execute`/`shell:allow-spawn` with `"sidecar": true`; args must match the declared list — [Embedding External Binaries](https://v2.tauri.app/develop/sidecar/). **[documented]**
- Shell plugin had CVE-2025-31477 (GHSA-c9pr-q8gx-3mgp), an `open` allowlist issue — [NVD CVE-2025-31477](https://nvd.nist.gov/vuln/detail/CVE-2025-31477). **[documented]**
- Rust ↔ JS IPC: `#[tauri::command]` functions, async commands preferred for heavy work ("Asynchronous commands are preferred in Tauri to perform heavy work"), `Result<T,E>` maps to resolve/reject with a serializable error, and `tauri::ipc::Channel<T>` streams chunks/progress from Rust to the frontend — [Calling Rust from the Frontend](https://v2.tauri.app/develop/calling-rust/). **[documented]**
- The updater's own docs recommend exactly this pattern for progress: "To send progress to the frontend, the page suggests using a command with a channel" — [Updater plugin](https://v2.tauri.app/plugin/updater/). **[documented]**

### Inferences
- Download with progress + resume: write a Rust command that uses `tauri_plugin_http::reqwest` (so one reqwest version is linked) with a streamed body, counts bytes and pushes `Progress{downloaded,total}` over a `Channel`; resume is a manual `Range: bytes=N-` request on retry (reqwest exposes headers; neither `plugin-http` nor `plugin-upload` document resume). SHA-256 verification is a few lines with the `sha2` crate. **[inference]**
- Do all install/uninstall file operations in Rust (`std::fs`), not through `plugin-fs` scopes: the JS-side scope model would otherwise have to allow `/Library/Audio/Plug-Ins/**` and `C:\Program Files\Common Files\VST3\**` to the webview, which widens the attack surface for no gain. `plugin-fs` is still handy for `watch` (plugin folders) and `plugin-dialog` for folder pickers. **[inference]**
- `plugin-store` (JSON key-value) is adequate for "last check time / channel / ignored versions" state. **[inference]**
- `plugin-shell` is needed only to launch an elevated helper or a vendor's own installer; for the manager's own operations, prefer in-process Rust. **[inference]**

### Gaps
- Whether `tauri-plugin-http` JS `fetch` exposes a streaming `ReadableStream` body (the permission names `fetch-read-body`/`fetch-cancel-body` suggest chunked reads, but the page does not document progress events).
- Whether `plugin-fs` scopes constrain Rust `std::fs` calls — the page does not say (they are enforced in the plugin's IPC commands, so almost certainly not, but that is inference).

## Q2. Privilege elevation from a Tauri app per OS, and which Rust crates do it

### Takeaway
There is no Tauri API for elevation; the updater plugin itself shows the three idioms Tauri's own maintainers use — **Windows: rely on the launched installer's manifest (`RequestExecutionLevel admin`) and let UAC prompt; macOS: `osascript "do shell script … with administrator privileges"`; Linux: `pkexec`, falling back to zenity/kdialog + `sudo -S`** — all of which work without any code signing. The signed-only paths (macOS `SMJobBless`/`SMAppService` helpers) are closed to Krate. The cleanest way to avoid elevation entirely on macOS and Linux is to install to the per-user VST3/AU folders; on Windows the per-user VST3 folder exists in the spec but is described as "mainly for development use".

### Cited Findings
**What Tauri's own updater does (primary source, `plugins/updater/src/updater.rs`, branch v2):**
- Windows: `Update::install_inner` launches the downloaded NSIS/MSI installer via `ShellExecuteW` with verb `"open"` — no `"runas"`; "Elevation is not requested explicitly. Any UAC prompt would come from the installer itself or its manifest"; the app runs `on_before_exit` then `std::process::exit(0)` — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**
- macOS: extracts `.app.tar.gz` with `flate2` + `tar` into a `tauri_updated_app` temp dir on the same mount, then `swap_bundle` via `libc::renamex_np(RENAME_SWAP)` with a rename-backup fallback; **on `PermissionDenied` it runs `do shell script … with administrator privileges` through the `osakit` crate on the main thread** (an osascript that calls `renamex_np`, falling back to `mv`); no `codesign`, `xattr` or quarantine handling appears; it `touch`es the bundle afterwards — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**
- Linux deb/rpm: `try_install_with_privileges` tries, in order, (1) `pkexec <dpkg -i | rpm -U> <pkg>`, (2) `get_password_graphically` (`zenity --password`, then `kdialog --password`) piped to `sudo -S`, (3) plain `sudo`; `gksudo`/`kdesudo` are not used; a failed `pkexec` falls through without checking its exit status — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**

**Windows:**
- Tauri's NSIS template sets `RequestExecutionLevel admin` for `perMachine`, `RequestExecutionLevel user` for `currentUser`, and `MULTIUSER_EXECUTIONLEVEL Highest` (MultiUser.nsh) for `both` — [installer.nsi](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). **[documented, source]**
- tauri-bundler 2.5.1 fixed "NSIS per-machine installer was not requesting elevation when run by non-admin users" — [tauri-bundler v2.5.1 release notes](https://v2.tauri.app/release/tauri-bundler/v2.5.1/). **[documented]**
- UAC prompt appearance for unsigned binaries: Microsoft's (archived, Vista-era) UAC blog describes "Yellow background and red shield icon marks an application that is unsigned or signed but not yet trusted" — [Microsoft UAC blog archive](https://learn.microsoft.com/pl-pl/archive/blogs/uac/whats-new-in-beta-2-user-experience); a current vendor page describes today's text, "Do you want to allow this app from an unknown publisher to make changes to your device" — [Advanced Installer](https://www.advancedinstaller.com/allow-app-from-unknown-publisher-make-changes.html). **[documented (old) / reported (current wording)]**
- `runas` crate 1.2.0 (mitsuhiko, docs.rs page dated 2026-10-21): "implements basic support for running a command in an elevated context"; **does not support capturing output**; Windows is always GUI mode (UAC), macOS GUI and CLI modes, Linux CLI (sudo) only; on Windows the working directory is always `system32` — [docs.rs/runas](https://docs.rs/runas). **[documented]**
- `elevated-command` 1.1.3 (vangork, last release 2026-09-26, MIT; 12 stars, 20 commits): wraps `std::process::Command`; README says Windows uses UAC, Linux uses `pkexec`, macOS "should behave just like the `sudo` command"; `Command::is_elevated()`; the app itself must not be run under sudo — [docs.rs/elevated-command](https://docs.rs/elevated-command), [GitHub vangork/elevated-command](https://github.com/vangork/elevated-command). **[documented]**
- Other crates seen: `run-as` 1.2.5 (2025-09-04, fork of runas) — [docs.rs/run-as](https://docs.rs/run-as); `self-runas` 0.1.0 (2025-08-18, relaunch self elevated) — [docs.rs self-runas](https://docs.rs/crate/self-runas/0.1.0); `sudo` (restarts the program under sudo) — [docs.rs/sudo](https://docs.rs/sudo). **[documented]**

**macOS:**
- `AuthorizationExecuteWithPrivileges` is marked deprecated in Apple's documentation (availability listed through macOS 10.7) — [Apple docs](https://developer.apple.com/documentation/security/authorizationexecutewithprivileges). **[documented]** It "doesn't verify that the executable hasn't been tampered with", yet many installers still use it — [Threatpost](https://threatpost.com/deprecated-insecure-apple-authorization-api-can-be-abused-to-run-code-at-root/127618). **[reported]**
- `SMAppService`/`SMJobBless` privileged helpers: an Apple DTS answer says the app and embedded helper must be "signed with the same Apple-issued code-signing identity. If, for example, you are using ad hoc signing (Sign to Run Locally in Xcode parlance) then you will see problems like this" (`SMAppServiceErrorDomain Code=1 "Operation not permitted"`) — [Apple Developer Forums thread 799910](https://developer.apple.com/forums/thread/799910); Apple's daemon-signing guide requires a Team and Hardened Runtime — [Signing a daemon with a restricted entitlement](https://developer.apple.com/documentation/xcode/signing-a-daemon-with-a-restricted-entitlement); under Sequoia an improperly signed daemon shows as "Item from unidentified developer" and does not run — [thread 757463](https://developer.apple.com/forums/thread/757463). **[reported, Apple forums]**
- Audio-plugin developers on the JUCE forum discuss the same problem (copying a plugin into a system location) and land on osascript/AppleScript elevation as the pragmatic route — [JUCE: How to copy a plugin in a system location](https://forum.juce.com/t/how-to-copy-a-plugin-in-a-system-location-sorting-out-root-privileges/14893), [JUCE: Elevated permissions in macOS](https://forum.juce.com/t/elevated-permissions-in-macos-or-so-we-thought-edited/55419). **[reported]**

**Linux:**
- `pkexec` runs a program as another user (root by default) after a PolicyKit authorization check; by default members of the `sudo` group may run any command after authenticating; `pkexec` does not forward `$DISPLAY`/`$XAUTHORITY`, so it is for non-GUI helper commands — [pkexec(1)](https://www.freedesktop.org/software/polkit/docs/0.106/pkexec.1.html). **[documented]**

**Per-user plug-in locations (avoids elevation):**
- VST3 spec: Windows user folder `%LOCALAPPDATA%/Programs/Common/VST3/` (priority 1, "mainly used for development use case"), global `/Program Files/Common Files/VST3/`; macOS user `~/Library/Audio/Plug-ins/VST3/` (priority 1), global `/Library/Audio/Plug-ins/VST3/`; Linux user `$HOME/.vst3/` (priority 1), global `/usr/lib64/vst3/` (Fedora), `/usr/lib/vst3/`, `/usr/local/lib64/vst3/`, `/usr/local/lib/vst3/`; hosts scan higher-priority locations first and take the first plug-in per Processor UID; symlinks are allowed — [VST3 Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html). **[documented]**

### Inferences
- Recommended elevation design (no certificates): keep the manager itself per-user (NSIS `currentUser`, `%LOCALAPPDATA%`) so its self-update never prompts; perform plugin installs via a **tiny CLI helper** shipped as a sidecar (`externalBin`) that takes a JSON job (`install|remove`, staged source path, destination), and launch it elevated: Windows `ShellExecuteExW` verb `runas` on the helper (UAC "unknown publisher" yellow prompt); macOS `osascript -e 'do shell script "<helper> <job>" with administrator privileges'` (the same mechanism the Tauri updater uses); Linux `pkexec <helper> <job>` with zenity/kdialog+`sudo -S` fallback (again mirroring the updater). Stage, verify and unpack as the user; only the final copy/rename/remove runs as root. **[inference]**
- Because `runas` cannot capture stdout, have the helper write a result file in a user-writable temp dir and exit codes, or use `elevated-command` (newer, less proven). **[inference]**
- Linux: default to `~/.vst3` (spec priority 1, no root needed) and offer system-wide as opt-in — this removes the whole polkit dependency for most Linux users. macOS: `~/Library/Audio/Plug-Ins/{VST3,Components}` likewise avoids admin prompts; whether all AU hosts rescan the user Components folder identically to `/Library` is a gap. Windows: Program Files is the practical default because the per-user folder is spec'd as "development use" and some hosts may not scan it. **[inference]**
- A persistent root helper (polkit action file, launchd daemon, Windows service) is unnecessary for an infrequent install action and, on macOS, impossible without signing. **[inference]**

### Gaps
- No Tauri-specific GitHub discussion on elevation was found; everything above is from the updater source, crate docs and OS docs.
- Which Windows DAWs actually scan `%LOCALAPPDATA%\Programs\Common\VST3` — not researched here.
- `elevated-command`'s exact Windows (ShellExecute `runas`?) and macOS (osascript?) mechanisms are not stated in its README; the source would need reading.

## Q3. `tauri-plugin-updater` with an UNSIGNED app on each OS

### Takeaway
The updater's own minisign signature is independent of OS code signing and is mandatory ("Signing cannot be turned off"), so **the updater works for unsigned apps on all three desktop OSes**: on Windows it re-runs the NSIS installer with `/UPDATE /P` (no UAC for a `currentUser` install; a UAC "unknown publisher" prompt on every update for `perMachine`); on macOS it swaps the `.app` bundle in place without writing a quarantine attribute (so Gatekeeper does not re-fire), but the **first** install of an unsigned/non-notarized download is the real problem and ad-hoc signing (`signingIdentity: "-"`) is needed on Apple Silicon; on Linux it overwrites the AppImage file in place or shells out to `pkexec dpkg/rpm`. Upgrade to ≥ 2.12.0 and set `requireSignedVersion: true` because of two September-2026 downgrade CVEs.

### Cited Findings
- "Tauri's updater needs a signature to verify that the update is from a trusted source. Signing cannot be turned off." Keys via `tauri signer generate -w ~/.tauri/myapp.key`; `pubkey` in `tauri.conf.json`; `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`) at build; "Losing the private key means you cannot publish updates to existing installs" — [Updater plugin](https://v2.tauri.app/plugin/updater/). **[documented]**
- Verification is minisign (`minisign_verify`) over the package bytes (prehashed mode); only after that does `verify_signed_version` read a `version:` field from the signature's trusted comment; `requireSignedVersion` (default `false`) rejects a mismatch — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs), [config.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/config.rs). **[documented, source]**
- Artifacts with `createUpdaterArtifacts: true`: Linux `.AppImage` + `.sig`; macOS `.app.tar.gz` + `.sig`; Windows NSIS `-setup.exe` and MSI each + `.sig`; `"v1Compatible"` (`.tar.gz`, `.nsis.zip`, `.msi.zip`) is slated for removal in v3; `.deb`/`.rpm` are not listed as updater artifacts on the docs page — [Updater plugin](https://v2.tauri.app/plugin/updater/). **[documented]** The changelog nonetheless states "Updater plugin now supports all bundle types: Deb, Rpm and AppImage for Linux; NSiS, MSI for Windows" (deb since 2.1.0) — [updater changelog](https://v2.tauri.app/release/updater/all-versions/), [updater v2.1.0](https://v2.tauri.app/release/updater/v2.1.0/). **[documented]**
- Static `latest.json`: required `version`, `platforms.<os>-<arch>.url` and `.signature` (the `.sig` file **contents**, not a URL); optional `notes`, `pub_date` (RFC 3339); platform keys `linux|darwin|windows` × `x86_64|aarch64|i686|armv7`; "Tauri validates the whole file before checking the version, so every platform entry must be complete"; endpoints may contain `{{target}}`, `{{arch}}`, `{{current_version}}`; a dynamic server returns 204 for no update; production endpoints must be HTTPS unless `dangerousInsecureTransportProtocol` — [Updater plugin](https://v2.tauri.app/plugin/updater/). **[documented]**
- The plugin also supports `{{bundle_type}}` and an `{os}-{arch}-{installer}` key lookup (e.g. to serve different files to deb vs AppImage installs); `installer_for_bundle_type` maps `tauri::utils::platform::bundle_type()` to `Deb|Rpm|AppImage|Msi|Nsis|App` — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**

**Windows:**
- `windows.installMode`: `passive` (default) — progress window, no interaction; `basicUi` — needs user interaction to finish; `quiet` — "The installer cannot request admin rights itself, so it only works for per-user installs or when the app already runs elevated" (not recommended); the app exits before installing "because of a Windows installer limitation", with an `on_before_exit` hook — [Updater plugin](https://v2.tauri.app/plugin/updater/). Exact flags: NSIS `passive → /P`, `quiet → /S`, `basicUi → []`; MSI `passive → /passive`, `quiet → /quiet`, `basicUi → /qb+`; the updater always adds `/UPDATE` (NSIS) or `/promptrestart` (MSI), plus `/R` and `/ARGS <current args>` when restarting — [config.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/config.rs), [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**
- In the NSIS template, `/UPDATE` skips the WebView2 fresh-install branch ("Skipped entirely when `UpdateMode` is 1"), skips Start-menu shortcut recreation and the uninstaller's app-data deletion; `/P` skips wizard pages and auto-closes; `/R` relaunches the app as the user after success — [installer.nsi](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). **[documented, source]**
- No GitHub issue specifically about UAC on `perMachine` updates was found; the closest is the bundler 2.5.1 elevation fix above and an analogous electron-builder/NSIS UAC thread — [ipfs-desktop PR 1679](https://github.com/ipfs/ipfs-desktop/pull/1679). **[reported, analogy]**

**macOS:**
- Mechanism: in-place `renamex_np(RENAME_SWAP)` of the `.app`, osascript admin fallback on `PermissionDenied`, no quarantine/xattr/codesign handling (see Q2) — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**
- A project PR reports "the in-app updater never sets the quarantine attribute, which is why the updater path has worked while browser downloads failed" — [penard-monkey/worktrees PR 568](https://github.com/penard-monkey/worktrees/pull/568). **[reported]** A separate test found files an unsigned Tauri app writes itself (reqwest download, zip extract) carry no quarantine — [yw0nam/YUI issue 1688](https://github.com/yw0nam/YUI/issues/1688). **[reported]**
- First launch of an unsigned download: Tauri docs say without signing "browser-downloaded apps can trigger a warning that the app is 'broken and can not be started'"; set `signingIdentity` to `"-"` for an ad-hoc signature, which "helps on Apple Silicon, where code-signing is required for all apps from the Internet", but "does not stop macOS from requiring users to approve the app in Privacy & Security settings"; notarization requires a paid Developer ID (USD 99/yr) and is "Not possible with a free Apple Developer account" — [Code Signing macOS](https://v2.tauri.app/distribute/sign/macos/). **[documented]**
- Multiple Tauri projects report the "damaged and can't be opened" error on unsigned DMG downloads, fixed by `signingIdentity: "-"`; one notes `codesign --verify` fails with "code has no resources but signature indicates they must be present" without it, and that Right-click → Open does not bypass the "damaged" variant — [WhimprFlow PR 2](https://github.com/nitrimandylis/WhimprFlow/pull/2), [toril PR 48](https://github.com/kovirlabs/toril/pull/48), [Yomu issue 1](https://github.com/ASHUTOSH-SWAIN-GIT/Yomu/issues/1). **[reported]**
- macOS Sequoia removed the Control-click "Open" bypass for unsigned apps; users must go to System Settings › Privacy & Security › "Open Anyway" after a failed launch — [AppleInsider](https://appleinsider.com/inside/macos-sequoia/tips/whats-changed-in-runtime-protection-for-macos-sequoia), [Cult of Mac](https://www.cultofmac.com/864843/macos-sequoia-removes-handy-shortcut-bypass-gatekeeper-security/); one tester found the right-click path shows the identical dialog — [TrozWare](https://troz.net/post/2024/sequoia_app_permissions/). **[reported]**
- A Japanese write-up confirms the updater's minisign `.app.tar.gz.sig` is separate from Apple code signing/notarization — [Classmethod](https://dev.classmethod.jp/articles/shuntaka-tauri-macos-codesign-notarization-updater-github-releases/). **[reported]**

**Linux:**
- AppImage: the payload must be ELF (or gzip with the `zip` feature); the running AppImage is renamed into a same-device `0700` temp dir (tries `temp_dir`, `dirs::cache_dir`, then the parent), the new bytes are written to the original path with the original permission bits re-applied, and the backup is renamed back on failure — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]**
- deb/rpm: `pkexec` → zenity/kdialog + `sudo -S` → `sudo` (see Q2) — [updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs). **[documented, source]** A project reports `rpm -U` "fails silently on rpm-ostree systems like Bazzite and Fedora Silverblue" — [sqlpilot PR 253](https://github.com/EVWorth/sqlpilot/pull/253). **[reported]**
- A Tauri app user hit "`APPDIR` or `APPIMAGE` environment variable found but this application was not detected as an AppImage" on NixOS/containers/Firejail; maintainers said it was an old-Tauri bug since fixed — [NextGraph issue 38](https://git.nextgraph.org/NextGraph/nextgraph-rs/issues/38). **[reported]**

**Security advisories (2026):**
- CVE-2026-95624 / GHSA-rjc6-5hfg-grp9: `check` accepted `allowDowngrades` from frontend JS (XSS → rollback); affected 2.8.0 ≤ v < 2.12.0; CVSS 6.8; published 2026-09-22 — [OSV](https://osv.dev/vulnerability/CVE-2026-95624). **[documented]** Fixed in updater 2.12.0 (2026-09-20): `allowDowngrades` moved to `plugins.updater` config (default `false`) — [updater v2.12.0 notes](https://v2.tauri.app/release/updater/v2.12.0/). **[documented]**
- CVE-2026-95625 / GHSA-j38x-g3m3-95fr: minisign covers only the binary; the manifest is unsigned, so a manifest-serving attacker can force installation of an older signed release; affected 2.0.0 ≤ v < 2.12.0; CVSS 5.9; published 2026-09-23 — [OSV](https://osv.dev/vulnerability/CVE-2026-95625). Mitigation is the `requireSignedVersion` option (version embedded in the signature's trusted comment) — [config.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/config.rs). **[documented]**

### Inferences
- For Krate: ship the manager per-user on Windows (`currentUser`), so self-update = silent `/UPDATE /P` with no UAC; the plugin-install step elevates separately (Q2). **[inference]**
- The NSIS `-setup.exe` downloaded by the updater is written by reqwest, not a browser, so it carries no Mark-of-the-Web → SmartScreen should not interpose on self-update (same reasoning as the macOS no-quarantine report); SmartScreen will interpose on the user's **first** browser download. **[inference]**
- On macOS, ad-hoc sign (`"-"`) both the shipped app and the update bundle; the first-run "Open Anyway" dance is unavoidable without notarization, but subsequent updates via the plugin are silent as long as the bundle stays user-writable (`/Applications` is writable by admin users; otherwise the osascript admin prompt fires). **[inference]**
- For Linux, publish AppImage as the updater-capable format and `.deb`/`.rpm` as "package-manager" formats; or accept the pkexec prompt on every deb/rpm update. **[inference]**

### Gaps
- No official statement that the updater is "supported" for unsigned macOS apps; the evidence is the source code (no signing checks) plus community reports. One third-party "skills" page claims the opposite ("Auto-updater requires valid code signing on all platforms") without evidence — treat as wrong.
- Behaviour when an ad-hoc-signed app is replaced by an update whose embedded ad-hoc signature differs — not tested anywhere I found.

## Q4. Linux: WebKitGTK 4.1 dependency, distro coverage, NVIDIA/Wayland rendering, packaging formats, what the AppImage bundles

### Takeaway
Tauri 2 hard-requires WebKitGTK **4.1** (`libwebkit2gtk-4.1-dev` / `webkit2gtk4.1-devel` / `webkit2gtk-4.1`), which Ubuntu 22.04+, Debian 12, Fedora and Arch all provide; the documented failure class is NVIDIA + WebKitGTK DMABUF (blank window, flicker, "Error 71" on Wayland) with a four-step workaround ladder ending in `WEBKIT_DISABLE_DMABUF_RENDERER=1`. The AppImage bundles WebKitGTK and everything else from the **build host** (hence 70+ MB and "build on Ubuntu 22.04"), is tied to that host's library layout, and a replacement "truly portable" bundler is still a draft PR; `.deb`/`.rpm` are small and use the system WebKit; Flatpak is documented (GNOME 46/47 runtime) but is a poor fit for an app that must write to `/usr/lib/vst3` or run `pkexec`.

### Cited Findings
- Prerequisites per distro: Debian/Ubuntu `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`; Arch `webkit2gtk-4.1 base-devel … libappindicator-gtk3 librsvg xdotool`; Fedora `webkit2gtk4.1-devel openssl-devel … libappindicator-gtk3-devel librsvg2-devel libxdo-devel` + `c-development`; openSUSE `webkit2gtk3-devel`; Alpine `webkit2gtk-4.1-dev` — [Prerequisites](https://v2.tauri.app/start/prerequisites/). **[documented]**
- AppImage: "Build on the oldest base system you intend to support that still provides WebKitGTK 4.1. Ubuntu 22.04 and Debian 12 are given as examples"; building on a newer system raises the glibc floor (`GLIBC_2.33' not found`); size "grows from the 2-6 MB range to 70+ MB"; `bundleMediaFramework` (GStreamer) "only fully supported on Ubuntu build systems"; extra files must be placed under `/usr/`; ARM AppImages cannot be cross-compiled (linuxdeploy), use `ubuntu-22.04-arm`/`ubuntu-24.04-arm` runners (~10 min/build) — [AppImage](https://v2.tauri.app/distribute/appimage/). **[documented]**
- Ubuntu 24.04 dropped `webkit2gtk-4.0`, pushing projects to 4.1 — [OrcaSlicer PR 5135](https://github.com/SoftFever/OrcaSlicer/pull/5135). **[reported]** On Noble a CI build saw two WebKitGTK versions (2.44.0 in universe, 2.48.7 in security) and the newer one picked up; the poster pinned 2.44 as a "known Tauri/AppImage problem" workaround — [xmr-btc-swap commit](https://git.hackliberty.org/Git-Mirrors/xmr-btc-swap/commit/a056ae3a47be1f922ec77daa9b060a485725d7bd). **[reported]** Moving an AppImage build from 22.04 to 24.04 raised the glibc requirement to 2.39 — [VoiceStudio PR 1007](https://github.com/debpalash/VoiceStudio/pull/1007). **[reported]**
- Portability of the current AppImage: Tauri PR #12491 "feat(bundler): Truly portable appimage (experimental)" (FabianLars) replaces linuxdeploy with a sharun-based bundler behind `useNewFormat` / `TAURI_BUNDLER_NEW_APPIMAGE_FORMAT`, runs the app once at bundle time to discover libraries, cannot cross-compile, and is **still a draft** (milestone 2.13; an Oct 6 2026 question "is the AppImage path still recommended?" is unanswered); it targets issues #10617, #10078, #6172 (`xdg-open`/`shell.open` failing on distros other than the build host) and #14208 — [tauri PR 12491](https://github.com/tauri-apps/tauri/pull/12491). **[reported, primary PR]** A user summary: "it's the AppImage what does not work except on Ubuntu" — [CodexMonitor issue 329](https://upd.dev/Dimillian/CodexMonitor/issues/329). **[reported]**
- Graphics: symptoms are blank/white window, flicker on resize, silent crash on resize, `AcceleratedSurfaceDMABuf was unable to construct a complete framebuffer`, `Gdk-Message: Error 71 (Protocol error) dispatching to Wayland display`; cause "the WebKitGTK DMABUF renderer requests buffer formats that the NVIDIA driver doesn't provide"; workaround order: (1) `nvidia_drm.modeset=1` for drivers < 545, (2) `__NV_DISABLE_EXPLICIT_SYNC=1` (fixes Error 71, no perf cost), (3) `WEBKIT_DISABLE_DMABUF_RENDERER=1` (disables the fast path), (4) `WEBKIT_DISABLE_COMPOSITING_MODE=1` (last resort, disables accelerated compositing); set in `main()` under `#[cfg(target_os = "linux")]` before the builder, referencing tauri-apps/tauri#9394 and WebKit bug 261874; the page warns not to ship it unconditionally; WebKitGTK masks the WebGL renderer string as "Apple GPU" — [Linux Graphics Issues](https://v2.tauri.app/develop/debug/linux-graphics/). **[documented]**
- With DMABUF disabled, CSS `backdrop-filter: blur()` stops working on RTX 50-series and other workarounds did not fix the blank view there — [WebKit bug 303811](https://bugs.webkit.org/show_bug.cgi?id=303811). **[reported]** NVIDIA DGX Spark white screen fixed by the same variable — [NVIDIA forums](https://forums.developer.nvidia.com/t/webkit-tauri-application-white-screen-on-dgx-spark-gpupermission-issues/348741/2). **[reported]** Nixpkgs sets the variable by default for Tauri apps — [nixpkgs commit](https://code.ornl.gov/nix/nixpkgs/-/commit/90f8af0c4f9e4db25f67bcf779e980b3344b9ed5). **[reported]** Shipping Tauri apps document the same env vars for users: [Yaak](https://yaak.app/docs/getting-started/linux-graphics-issues), [Defguard](https://docs.defguard.net/support-1/troubleshooting-guides/desktop-client/client-crashes-immediately-on-launch-with-error-71-protocol-error-dispatching-to-wayland-display). **[reported]**
- Flatpak: manifest uses `org.gnome.Platform` 47 (local prerequisites say 46); built from the `.deb`; permissions `--socket=wayland --socket=fallback-x11 --device=dri --share=ipc`; `WEBKIT_DISABLE_COMPOSITING_MODE=1` "may fix black webviews on Wayland"; the page does not address the updater or host command execution — [Flatpak](https://v2.tauri.app/distribute/flatpak/). **[documented]**
- Linux harness caveat already known in this repo: no run loop in bare test harnesses (not Tauri-specific; noted for completeness).

### Inferences
- Krate should ship `.deb` + `.rpm` (system WebKit, 2–6 MB) as the primary Linux formats and an AppImage built on `ubuntu-22.04` as the fallback/updater format; expect AppImage reports from Fedora/Arch users until PR #12491 lands. **[inference]**
- Do not pursue Flatpak for a system-folder installer: the sandbox blocks `pkexec`/`/usr/lib/vst3` writes without `--talk-name=org.freedesktop.Flatpak` host escapes; `~/.vst3` installs would work from a sandbox only with an explicit `--filesystem=~/.vst3` permission. **[inference]**
- Ship the NVIDIA env-var toggle as a **user setting** (or detect `nvidia` kernel module) rather than unconditionally, per the docs' warning. **[inference]**

### Gaps
- Could not fetch Tauri's AppImage build template (`crates/tauri-bundler/src/bundle/linux/templates/appimage`, 404 on both raw and HTML paths — it may have moved), so the exact list of bundled libraries (WebKitWebProcess/NetworkProcess, injected bundle) is unverified; the docs' "bundles all dependencies" and PR #12491's "tied to the build host's libraries" are the evidence.
- No Wayland-specific issue list beyond "Error 71" was found in the official docs.

## Q5. Windows: WebView2 runtime options, NSIS vs MSI, per-user vs per-machine

### Takeaway
Use NSIS with `installMode: currentUser` (default; `%LOCALAPPDATA%`, no admin) and `webviewInstallMode: downloadBootstrapper` (0 MB; WebView2 is preinstalled on Windows 10 1803+/11); `embedBootstrapper` (+1.8 MB) is the offline-safer choice and `offlineInstaller` (+127 MB) / `fixedRuntime` (+180 MB) are for air-gapped or pinned-WebView2 cases. MSI needs WiX v3, VBScript and a Windows build host; NSIS can also be cross-compiled.

### Cited Findings
- WebView2 modes: `downloadBootstrapper` (default, needs internet, +0 MB); `embedBootstrapper` (needs internet, ~+1.8 MB, better Windows 7 MSI support); `offlineInstaller` (offline, ~+127 MB); `fixedRuntime` (offline, ~+180 MB, you patch WebView2 yourself; extract the `.cab` into `src-tauri` and set `path`); `skip` (+0 MB, "Your application WILL NOT work if the user does not have the runtime installed"); "Windows 10 (April 2018 or later) and Windows 11 include WebView2 with the OS" — [Windows Installer](https://v2.tauri.app/distribute/windows-installer/). **[documented]**
- MSI (WiX v3): Windows-only build; needs the VBSCRIPT optional feature ("failed to run light.exe" otherwise); custom template/fragments/localization; `TAURI_BUNDLER_WIX_FIPS_COMPLIANT`. NSIS (`-setup.exe`): cross-compilable from Linux/macOS ("less straightforward and less tested"); custom template, installer hooks, language selector — [Windows Installer](https://v2.tauri.app/distribute/windows-installer/). **[documented]**
- NSIS `installMode`: `currentUser` (default, no admin, `%LOCALAPPDATA%`); `perMachine` (Program Files, admin); `both` (user chooses; needs admin to run) — [Windows Installer](https://v2.tauri.app/distribute/windows-installer/); template `RequestExecutionLevel` mapping in [installer.nsi](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). **[documented]**
- The installer checks WebView2 via the EdgeUpdate `pv` registry value (HKLM WOW6432Node, then HKCU), downloads/extracts the bootstrapper to `%TEMP%` and runs it with `/install`, aborting on a non-zero exit; a configured minimum WebView2 version triggers the EdgeUpdate-based updater even on `/UPDATE` — [installer.nsi](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi). **[documented, source]**
- Architectures: host arch by default; `--target i686-pc-windows-msvc` for 32-bit; `--target aarch64-pc-windows-msvc` for ARM64 (needs VS "C++ ARM64 build tools"; the NSIS installer itself runs as x86 under emulation, the app is native) — [Windows Installer](https://v2.tauri.app/distribute/windows-installer/). **[documented]**
- Unsigned downloads: SmartScreen reputation "must build for each new version of your files, starting with zero reputation" and cannot transfer between versions "unless both were signed using the same publisher identity"; Windows 11 Smart App Control "will block execution of unsigned files unless the file has a positive reputation" — [Microsoft Learn: SmartScreen reputation](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation). **[documented]** Open-source projects document the "More info → Run anyway" step for users — [open-bart](https://open-bart.readthedocs.io/en/latest/standalone/SMARTSCREEN.html), [BleachBit](https://www.bleachbit.org/microsoft-defender-smartscreen). **[reported]**
- The Prerequisites page lists Windows 7+ as supported and WebView2 preinstalled since Windows 10 1803 — [Prerequisites](https://v2.tauri.app/start/prerequisites/). **[documented]**

### Inferences
- A per-user manager that elevates a sidecar helper only for `C:\Program Files\Common Files\VST3` writes gets: no UAC on install/self-update of the manager, one UAC prompt per plugin install batch. Every first-time download of the unsigned `-setup.exe` will show SmartScreen "Windows protected your PC" and Smart App Control (when enabled) will block it outright — unavoidable without a certificate; document the hash-verification route. **[inference]**
- Skip MSI entirely: it adds a WiX/VBScript toolchain and a Windows-only build for no benefit here (no Group Policy deployment requirement). **[inference]**

### Gaps
- No measured SmartScreen behaviour for files written by reqwest (no MOTW) was found; the "no MOTW → no SmartScreen" expectation is inference.

## Q7. Frontend: plain TypeScript with Node.js tooling? How much Rust?

### Takeaway
Yes — `create-tauri-app` offers Vanilla-TS, Svelte, React, Vue, Solid, Preact and Angular templates on Vite with npm/pnpm/yarn/bun, so the UI is ordinary Node.js-tooled TypeScript; the Rust side is a thin set of `#[tauri::command]`s. For this scope I estimate **~1,200–2,000 lines of Rust** (plus a ~200–400-line elevated helper CLI), because downloads, checksums, archive extraction, scanning plugin folders and the privileged copy/remove belong in Rust; the JS side is view + state only.

### Cited Findings
- Templates: TypeScript/JavaScript — Vanilla, Vue, Svelte, React, Solid, Angular, Preact (TS or JS flavor); Rust — Vanilla, Yew, Leptos, Sycamore; .NET — Blazor; package managers pnpm/yarn/npm/bun (deno in manual setup); `npm create tauri-app@latest` or `cargo install create-tauri-app --locked` — [Create a Project](https://v2.tauri.app/start/create-project/). **[documented]**
- Node.js LTS is required "only if using a JavaScript frontend framework" — [Prerequisites](https://v2.tauri.app/start/prerequisites/). **[documented]**
- Commands, async commands for heavy work, `Result` errors, `Channel` streaming, `AppHandle`/`State` injection, events (`emit`/`listen`) — [Calling Rust from the Frontend](https://v2.tauri.app/develop/calling-rust/). **[documented]**
- Rust-side the updater exposes `download_and_install` with progress/finished callbacks and `app.restart()`; JS side `downloadAndInstall` emits `Started{contentLength}` / `Progress{chunkLength}` / `Finished` and `relaunch()` from `@tauri-apps/plugin-process` — [Updater plugin](https://v2.tauri.app/plugin/updater/). **[documented]**

### Inferences
- Rust LOC estimate by module (my estimate, not measured): plugin-folder scan + bundle version read (`Info.plist` / `moduleinfo.json` / PE resources) 150–300; feed fetch + semver compare 80–120; streamed download with progress + resume + SHA-256 150–250; archive extraction (`zip`, `tar`+`flate2`) 100–200; staging + elevated-helper invocation per OS (`cfg` blocks, ShellExecuteExW `runas` / osascript / pkexec) 250–400; uninstall 80–150; updater wiring, store, logging, error enum, `main.rs` 150–250; the sidecar helper CLI 200–400. Total ≈ 1.2–2.0 k lines of Rust, well within a C++ team's reach. **[inference]**
- Heavy logic should live in Rust commands: the webview has no raw filesystem/process access except through scoped plugins, and the sensitive operations (verify-then-install) should not be driveable from JS with arbitrary paths (cf. CVE-2026-95624's lesson about trusting the webview). JS/TS = rendering, state, i18n. **[inference]**

### Gaps
- No published LOC figures for a comparable Tauri installer/launcher were found; the estimate is mine.

Even privately that is < $2 per release across four legs. **[inference]**

## Q9. Binary sizes and memory in practice for a small app

### Takeaway

### Cited Findings
- Tauri docs: Linux `.deb`/`.rpm` sit "in the 2-6 MB range" while the AppImage "grows … to 70+ MB" — [AppImage](https://v2.tauri.app/distribute/appimage/). **[documented]**

- Universal macOS binaries roughly double the bundle — [zenn.dev](https://zenn.dev/8beeeaaat/articles/608b9ac5b76196). **[reported]**

### Inferences
- For Krate's manager (one window, a list, a few dialogs): expect ~5–10 MB NSIS exe, ~5–10 MB DMG per arch, ~3–6 MB deb/rpm, ~70–90 MB AppImage; idle RSS dominated by the webview process (tens of MB). **[inference]**

- No controlled, same-machine benchmark of a Tauri 2.12 app on all three OSes was found.

## Overall feasibility summary (inference, drawn from the findings above)

1. **Feasible without any certificate.** The updater's minisign scheme is independent of OS signing; the plugin itself already contains the three OS elevation idioms Krate would reuse for plugin installs (installer manifest / `osascript … with administrator privileges` / `pkexec` + `sudo -S`).
2. **The cost is the first launch, not the updates**: SmartScreen "Run anyway" (and a hard block under Smart App Control) on Windows; "Open Anyway" in Privacy & Security on macOS Sequoia+ with ad-hoc signing mandatory on Apple Silicon; AppImage fragility on non-Ubuntu Linux. Subsequent updates are silent/unprompted in the per-user configuration.
3. **Design levers that remove prompts**: per-user manager install (`currentUser`, no UAC on self-update); default to `~/.vst3` and `~/Library/Audio/Plug-Ins` on Linux/macOS; elevate only a sidecar helper, once per install batch; keep the manager updater on ≥ 2.12.0 with `requireSignedVersion: true` and `allowDowngrades: false`.
4. **Rust footprint** ≈ 1.2–2 k lines plus a small helper; UI is ordinary Vite + TypeScript with Node tooling; CI is the documented four-leg tauri-action matrix, free on public repos.
5. **Open risks**: Linux NVIDIA/Wayland rendering (ship the env-var toggle), AppImage portability pending PR #12491, Sequoia/Tahoe first-run friction, and `rpm -U` silently failing on immutable Fedora variants if deb/rpm self-update is used.
