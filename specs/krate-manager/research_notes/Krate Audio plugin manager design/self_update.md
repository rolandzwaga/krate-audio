# Self-update mechanisms for an unsigned, open-source, cross-platform desktop app (Windows / macOS / Linux), state as of 2026-10-29

Scope: the Krate Audio "plugin manager" (one window, list of plugins), candidate frameworks Tauri 2 / Electron / Qt-C++, no code-signing certificates ever, distribution via GitHub Releases plus a static JSON feed on GitHub Pages.

Conventions used below: **[DOC]** = documented behaviour in official docs or primary source code; **[ISSUE]** = reported in an issue tracker / forum / release note; **[INF]** = my inference. Library versions and dates are given where the source states them.

---

## Key question 1 — Libraries: per-OS mechanics, requirements, failure modes

### Takeaway
Of the ready-made libraries, only **tauri-plugin-updater (2.14.1)** and **Velopack (1.2.x)** are documented to install updates on all three OSes without any platform code-signing certificate; **electron-updater hard-requires an Apple-signed app on macOS** (Squirrel.Mac), which rules it out for an unsigned macOS build. Sparkle 2 works on ad-hoc-signed apps with EdDSA signatures but is macOS-only (WinSparkle covers Windows, nothing covers Linux); Squirrel.Windows is effectively unmaintained; AppImageUpdate is "beta-level code" with only alpha tags.

### Cited Findings

#### tauri-plugin-updater (v2) — latest release 2.14.1
- Manifest: required fields are `version`, `platforms.[target].url`, `platforms.[target].signature`; `notes` and `pub_date` are optional; `version` must be SemVer (leading `v` allowed); `pub_date` must be RFC 3339; `signature` is "the content of the generated `.sig` file. A path or URL does not work!"; Tauri validates the whole file before checking the version, so every platform entry must be complete — [DOC: Tauri v2 updater guide](https://v2.tauri.app/plugin/updater/)
- Platform keys are `OS-ARCH` with OS ∈ {`linux`, `darwin`, `windows`} and ARCH ∈ {`x86_64`, `aarch64`, `i686`, `armv7`}; the source also looks up `{os}-{arch}-{installer}` first, then `{os}-{arch}` — [DOC guide](https://v2.tauri.app/plugin/updater/); [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Dynamic server mode: respond `204 No Content` for "no update", or `200` with JSON containing `version`, `url`, `signature` (+ optional `notes`, `pub_date`) — [DOC guide](https://v2.tauri.app/plugin/updater/)
- Signing: keys generated with `tauri signer generate`; private key given to the bundler via `TAURI_SIGNING_PRIVATE_KEY` (path or content) and optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; ".env files do not work!"; `pubkey` in `tauri.conf.json` "cannot be a file path!"; signing "cannot be disabled"; losing the private key means you cannot publish updates to existing installs — [DOC guide](https://v2.tauri.app/plugin/updater/)
- Verification is minisign: the plugin uses the `minisign_verify` crate (`public_key.verify(data, &signature, true)`); the signature's trusted comment carries a `version:` field and `verify_signed_version` compares it to the announced version when `require_signed_version` is set — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs); 2.13.3 "Update `minisign-verify` to 0.3, which rejects signatures with a non-canonical Ed25519 `S` value"; 2.14.0 "`Update::install` now verifies the package bytes before installing them" and "Restored updates always require the signature to bind the announced version" — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md)
- Artifacts: `createUpdaterArtifacts: true` (v2 format) or `"v1Compatible"` (removed in v3). Windows: NSIS `-setup.exe` and MSI each with `.sig` (v1Compatible wraps them in `.nsis.zip` / `.msi.zip`); macOS: `.app.tar.gz` + `.sig`; Linux v2: raw `.AppImage` + `.sig` (v1Compatible: `.AppImage.tar.gz`) — [DOC guide](https://v2.tauri.app/plugin/updater/)
- **Windows install mechanics**: installer is written to a kept temp dir named `{app}-{version}-installer`, `on_before_exit` hook runs, installer launched via `ShellExecuteW` with verb `"open"` and `SW_SHOW` (no `runas`, no PowerShell), then `std::process::exit(0)`. NSIS args: `install_mode.nsis_args()` + `/UPDATE` (+ `/R` and `/ARGS <escaped current args>` when `restart_after_install`) + `installerArgs`. MSI: `%SYSTEMROOT%\System32\msiexec.exe /i "<path>" <mode args> /promptrestart <installerArgs>` (+ `AUTOLAUNCHAPP=True` for restart) — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Install-mode → flags: `passive` (default) → NSIS `/P`, msiexec `/passive`; `quiet` → NSIS `/S`, msiexec `/quiet`; `basicUi` → NSIS none, msiexec `/qb+`. Doc comment on `Quiet`: "Requires admin privileges if the installer does." — [DOC source config.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/config.rs); guide: `quiet` "only works in user-wide installations or when your app itself already runs with admin privileges"; "the application is automatically exited when the install step is executed" — [DOC guide](https://v2.tauri.app/plugin/updater/)
- `restartAfterInstall` / `restart_after_install` option added for Windows in 2.11.0; `on_before_exit` hook added in 2.0.0-beta.4 — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md)
- **macOS install mechanics**: tar extracted (first path component stripped) into a temp dir on the same device as the app (system temp or the app's parent), extraction dir chmod `0755`; replacement tries an atomic `renamex_np` with `RENAME_SWAP`, falls back to `replace_bundle` (two renames, restores the original on failure); on `PermissionDenied` it sets `need_authorization` and runs the same swap via AppleScript `do shell script ... with administrator privileges` on the main thread; afterwards it `touch`es the bundle and does **not** relaunch (the app must call `relaunch()`); the old app lands in the temp dir which is removed on drop; on failure `keep_backup_if_not_restored` may move the old app beside the target or into the home folder — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs); 2.5.0 "Fix update installation on macOS when using an user without admin privileges" — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md); README sample calls `relaunch()` after `downloadAndInstall()` with a comment that Linux/macOS must relaunch to run the new version — [DOC README](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/README.md)
- **Linux install mechanics (correction to the brief: deb/rpm ARE supported now)**: 2.1.0 "Added support for `.deb` package updates on Linux systems"; 2.10.0 "Updater plugin now supports all bundle types: Deb, Rpm and AppImage for Linux" — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md). AppImage: target path is the current executable path; checks gzip or ELF magic (2.14.0 "reject an AppImage update that is neither an AppImage nor a compressed AppImage"); moves the current file aside with `rename` (same device required; 2.14.0 fixed a cross-device link failure), then `std::fs::write`s the new file over the target and restores permissions; if the write fails it renames the backup back — i.e. move-aside-then-write, not write-temp-then-rename. Deb/RPM: package written to temp, installed with `pkexec dpkg -i` / `pkexec rpm -U`, falling back to a `zenity`/`kdialog` password piped to `sudo -S`, then plain `sudo`; failure returns `PackageInstallFailed` — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Transport: `endpoints` is an array; HTTPS enforced in release builds unless `dangerousInsecureTransportProtocol: true`; failover to the next endpoint only on a non-2XX status; URL variables `{{current_version}}`, `{{target}}`, `{{arch}}` only — [DOC guide](https://v2.tauri.app/plugin/updater/); 2.14.0 "Log a warning when the download URL of an update does not use `https`" — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md)
- Downgrades blocked by default; `version_comparator` can allow them; 2.12.0 (breaking) removed the JS `allowDowngrades` argument from `check` because "any code running in the webview could pass `allowDowngrades: true`"; it is now plugin config, default `false` — [DOC guide](https://v2.tauri.app/plugin/updater/); [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md)
- Requirements: Rust ≥ 1.90; desktop only (Android/iOS unsupported) — [DOC README](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/README.md)
- Reported field issue (other projects, same pattern): Nuxeo Drive hit `PermissionError` moving `.app` → `.app.old` in `/Applications` for a non-admin user; workaround was `~/Applications` — [ISSUE NXDRIVE-2163](https://jira.nuxeo.com/browse/NXDRIVE-2163). Addigy explains the general cause: macOS restricts write access to `/Applications` to administrators — [ISSUE/explainer Addigy](https://support.addigy.com/hc/en-us/articles/29415164222995)

#### electron-updater (electron-builder) — docs for "next (v27)" line, v26 current stable at fetch time
- Targets: Windows NSIS ("Squirrel.Windows is not supported"); macOS DMG + zip ("Squirrel.Mac requires both dmg and zip to be enabled"); Linux AppImage, DEB, RPM, Pacman — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); [DOC mac target](https://www.electron.build/docs/mac/)
- **Hard macOS requirement (confirmed)**: "macOS application must be signed in order for auto updating to work." — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); Electron: "`Squirrel.Mac` requires the app to be signed for automatic updates to work at all." — [DOC Electron code-signing tutorial](https://www.electronjs.org/docs/latest/tutorial/code-signing); Electron API docs: "Your application must be signed for automatic updates on macOS. This is a requirement of Squirrel.Mac." — [DOC Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater); maintainer develar, 2017-11-22: "Yes, app must be signed. It is requirement of Squirrel.Mac."; docs fixed 2018-10-30 by commit "docs: Code signing is required on macOS" — [ISSUE electron-builder #2326](https://github.com/electron-userland/electron-builder/issues/2326)
- Ad-hoc signing does not help: `mac.sign.identity: "-"` gives an ad-hoc signature "which will only run on the machine that built it" — [DOC mac target](https://www.electron.build/docs/mac/); an app project found the ad-hoc designated requirement is `cdhash H"…"` of that one build, so no later release can satisfy it, and Squirrel.Mac refuses — [ISSUE plasma PR #41](https://github.com/pankajyadav05/plasma/pull/41); another project likewise disabled auto-update until a Developer ID exists — [ISSUE lila-modeler #486](https://github.com/AlambritoDito/lila-modeler/issues/486)
- Differential updates: NSIS and the macOS zip publish a `.blockmap` per artifact; AppImage embeds its map; blockmap format `v3` (binary) default when `electronUpdaterCompatibility >= 7`, needs electron-updater ≥ 7.0.0-alpha.13; `v2` (gzipped JSON) for older clients; electron-updater 6 falls back to a full download on a `v3` map — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); `differentialPackage` default `true` — [DOC NSIS](https://www.electron.build/docs/nsis/)
- Providers: generic = static files over HTTP(S) (`latest*.yml` + release files uploaded manually); GitHub provider uses public releases by default and only hits the GitHub API for private repos with `GH_TOKEN` ("very special" cases); docs quote 5000 req/user/hour and up to 3 requests per update check — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- `latest.yml`: `version`, `releaseDate`, `files[] {url, sha512, size}`, optional `stagingPercentage` 0–100; v27 drops the legacy top-level `path`/`sha512` — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); [DOC v27 breaking changes](https://www.electron.build/docs/migration/v27-breaking-changes/)
- Install: `quitAndInstall({ isSilent, isForceRunAfter, waitUntilNextLaunch })`; `autoInstallEvent` ∈ `manual` / `onQuit` (v27 default) / `onNextLaunch` (planned v28 default); per-user NSIS installs can be installed automatically at next launch; per-machine NSIS (`isAdminRightsRequired`) is skipped by the automatic path "because it shows a UAC prompt" and needs an explicit `installPendingUpdateIfAvailable()`; Deb/RPM/Pacman "always elevate (pkexec/sudo), so they are skipped by the automatic path" — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- Windows verification: "Code signature validation is performed on Windows and macOS"; v27 "Windows update signature verification fails closed"; `migrate-schema` prints an advisory for `win.sign: false/null` unless `win.verifyUpdateCodeSignature` is `false`; Linux packages are not signed, `allowUnverifiedLinuxPackages` defaults to `true` — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); [DOC v27 breaking changes](https://www.electron.build/docs/migration/v27-breaking-changes/)
- Signed update manifests (v27): each `latest*.yml` is signed with Ed25519 at publish (`npx electron-builder create-update-key`, `ELECTRON_BUILDER_UPDATE_SIGN_KEY` / `_FILE`); public key auto-embedded as `updateManifestPublicKey` in `app-update.yml`; apps built with a key "fail closed" (`ERR_UPDATER_MANIFEST_NOT_SIGNED`, `ERR_UPDATER_MANIFEST_SIGNATURE_INVALID`); signed fields are `version`, `stagingPercentage`, `minimumSystemVersion`, each file's `url`/`sha512`/`size`; cosmetic fields not covered; publishing fails unless a key resolves, opt-out `updateManifest: false`; the page does not say this replaces Apple signing — [DOC Signed Update Manifests](https://www.electron.build/docs/features/signed-update-manifests/)
- Linux AppImage: `appimage-filename-updated` event after the file is moved to its final location; "APPIMAGE env is not defined" is a known log line with a manual `process.env.APPIMAGE` workaround not recommended for production — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- 2020 security history: Doyensec found a signature-validation bypass leading to RCE in electron-updater — [ISSUE/blog Doyensec](https://blog.doyensec.com/2020/02/24/electron-updater-update-signature-bypass.html)

#### Velopack — crate 1.2.161 on docs.rs at fetch time
- Positioning: "an installation and auto-update framework for cross-platform desktop applications"; bindings "Ready": C#, Rust, JavaScript, C++, Python; Java/Swift/Go planned; releases can be hosted on "any location that serves static files, such as cloud file storage or GitHub Releases" — [DOC intro](https://docs.velopack.io/)
- Outputs: `{id}-{ver}-full.nupkg`, `{id}-{ver}-delta.nupkg` (only if a previous release exists), `{id}-Portable.zip`, `{id}-Setup.exe`, `releases.{channel}.json` (the index `UpdateManager` reads), `RELEASES` (legacy Squirrel), `assets.{channel}.json`; any option can be set as `VPK_<OPTION>` env var; four-part versions unsupported — [DOC packaging overview](https://docs.velopack.io/packaging/overview)
- Signing stance (general): "signing is not required for local builds or testing", "you should always code-sign your application before distributing", "If you do not code-sign, your application may fail to run" — [DOC packaging overview](https://docs.velopack.io/packaging/overview); FAQ: "Unsigned applications are more likely to be flagged by antivirus software and Windows SmartScreen" — [DOC FAQ](https://docs.velopack.io/troubleshooting/faq)
- **Windows**: default install `%LocalAppData%\{packId}` via `Setup.exe` which "does not require elevation or use privileged directories"; `Setup.exe --installto {dir}` override; per-machine MSI installs to `Program Files\{publisher}\{packTitle}` (HKLM, requires elevation); layout is `current/` + root `Update.exe` + root `YourApp.exe` execution stub; on update "the entire `current` directory will be replaced"; if locked it tries to kill processes inside `current`, may prompt the user to kill other lockers or abort, and if it cannot identify the locker "the old version of the application will be launched"; signing "very recommended (but not required)", unsigned apps "may be flagged as a virus" — [DOC Windows](https://docs.velopack.io/packaging/operating-systems/windows)
- **macOS**: builds the `.app` (needs `.icns`), a `.pkg` (which it "generates and signs automatically" and which lets users pick `/Applications` or `~/Applications`), and a portable `.zip`; no DMG. "Code signing and notarization is required by Apple before shipping your releases to users, or your app won't run." A Velopack `.app` "doesn't need to be in `/Applications` to update"; packages download to `~/Library/Caches/velopack/{packId}/packages`; the bundle is "extracted and replaced in place"; if in `/Applications` "the updater uses AppleScript to request elevation"; App Sandbox not supported — [DOC macOS](https://docs.velopack.io/packaging/operating-systems/macos); installer page: if signing is configured the installer is also signed, "(This is required on MacOS)" — [DOC installer](https://docs.velopack.io/packaging/installer)
- **Linux**: "Velopack does not create an installer, it simply creates an `.AppImage` file"; updates download to `/var/tmp` then the `.AppImage` is replaced; "If the `.AppImage` is in a privileged folder, the updater will automatically prompt for sudo using `pkexec`"; `--compression gzip|xz`; `--categories` — [DOC Linux](https://docs.velopack.io/packaging/operating-systems/linux)
- Deltas: "Delta packages use Zstandard to create binary patches of individual files in your package"; per-file, 2 GB per-file cap; modes `None` / `BestSpeed` (default) / `BestSize`; client applies deltas in sequence to the cached package; heuristic may "download the latest full release instead"; for GitHub Releases "each release must contain one full package and one delta"; `vpk download` fetches the previous release in CI — [DOC deltas](https://docs.velopack.io/packaging/deltas)
- C++ binding: "Download the latest `velopack_libc_{version}.zip` from GitHub Releases" (pre-compiled dynamic lib, `lib` and `lib-static` dirs); `Velopack::VelopackApp::Build().Run();` must be the first statement; `UpdateManager manager("<url>")`, `CheckForUpdates()`, `DownloadUpdates()`, `WaitExitThenApplyUpdate()` then `exit(0)`; "the C / C++ library has no single apply-and-restart helper" — [DOC C++ quick start](https://docs.velopack.io/getting-started/cpp)
- GitHub source: `GithubSource` "Retrieves available releases from a GitHub repository. Supports both github.com and GitHub Enterprise instances."; `access_token` optional — without one requests are "rate limited to 60 req/hr per IP"; `prerelease` flag — [DOC docs.rs GithubSource 1.2.161](https://docs.rs/velopack/latest/velopack/sources/struct.GithubSource.html)
- Field use: Quiver 3.0.0 "now ships with Velopack for self-update across Windows / Linux / macOS" — [ISSUE/release note newreleases.io Quiver](https://newreleases.io/project/github/tgeorgiadis/quiver/release/v3.0.0-rc.1)

#### Sparkle 2 (macOS native) and WinSparkle (Windows native)
- Sparkle: "you must cryptographically sign your updates" (EdDSA via `generate_appcast` — "the recommended method" — or `sign_update`); keys via `./bin/generate_keys` stored in the login Keychain, public key in `Info.plist` `SUPublicEDKey`; archives must preserve symlinks or the code signature breaks; `generate_appcast` also emits `*.delta` files — [DOC Sparkle publishing](https://sparkle-project.org/documentation/publishing/); [DOC Sparkle documentation](https://sparkle-project.org/documentation/)
- Apple signing is recommended, not stated as mandatory: "Notarize and code sign the application via Apple's Developer ID program (if possible)"; key rotation only when you "both code-sign your application with Apple's Developer ID program and include a public EdDSA key"; ad-hoc warning: "the system may not let your application load Sparkle if you attempt to sign to run locally via an ad-hoc signature" (Library Validation under Hardened Runtime); Sparkle "will not notify your user if an update cannot be performed" (read-only mount, app translocation) by default — [DOC Sparkle documentation](https://sparkle-project.org/documentation/)
- Maintainer (zorgiepoo) on ad-hoc apps: "Sparkle's test app goes through the same process (EdDSA signing + adhoc-signed)"; Sparkle refuses when "A public (Ed)DSA key was found in the old bundle but no public (Ed)DSA key was found in the new update" — it "only supports rotation, but not removal of (Ed)DSA keys" — [ISSUE Sparkle discussion #2401](https://github.com/sparkle-project/Sparkle/discussions/2401); Scrivener's user-facing wording of the rule: "needs to be code-signed or its updates need to be signed with an EdDSA key" — [ISSUE Literature & Latte forum](https://forum.literatureandlatte.com/t/error-message-auto-update-not-configured-sparkle/130196)
- Security history: CVE-2025-0509, "A security issue was found in Sparkle before version 2.6.4" (EdDSA check bypass) — [ISSUE NVD CVE-2025-0509](https://nvd.nist.gov/vuln/detail/CVE-2025-0509); fix discussion — [ISSUE Sparkle #2551](https://github.com/sparkle-project/Sparkle/discussions/2551)
- Sandboxed apps need the Installer XPC Service (`SUEnableInstallerLauncherService`), "This service lets Sparkle install updates outside of your application's sandbox"; Sparkle's XPC services are ad-hoc signed with Hardened Runtime — [DOC Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/)
- WinSparkle: "App update framework for Windows, inspired by Sparkle for macOS", same appcast format; updates must be signed, EdDSA (Ed25519) current via `winsparkle-tool`, DSA deprecated; C API with C#/.NET, Python, Go, Pascal bindings; MIT; the README does not describe how the downloaded installer is run and does not mention Authenticode — [DOC WinSparkle README](https://github.com/vslavik/winsparkle)

### Inferences
- [INF] For an app that will never hold an Apple certificate, electron-updater is disqualified on macOS by documented behaviour, not by a reported bug; the new Ed25519 manifest signing in v27 does not change that because Squirrel.Mac validates the installed app's code-signing requirement, not the manifest.
- [INF] tauri-plugin-updater and Velopack both treat OS code signing as "recommended for Gatekeeper/SmartScreen", while their own tamper protection is independent (minisign in Tauri; Velopack's own package index — see Gaps). Neither source read for this note contains a check that refuses an unsigned/ad-hoc `.app`, and Velopack's macOS page explicitly says the `.app` may live outside `/Applications` and updates in place.
- [INF] On an unsigned macOS app the only platform-level consequence of an in-place bundle swap is Gatekeeper's first-launch quarantine prompt returning if the downloaded file carries the quarantine xattr; Tauri's `renamex_np` swap and Velopack's AppleScript elevation both sidestep the signature-seal problem that signed apps have.
- [INF] Sparkle + WinSparkle would give best-in-class native UX but need two code paths plus a third for Linux, which does not fit a one-window Tauri/Electron app; they are the right choice only if the manager is written in Qt/C++.

### Gaps
- I did not find a Velopack doc or issue stating what Velopack does with an unsigned or ad-hoc-signed macOS `.app` beyond Gatekeeper warnings; the `/packaging/installer` sentence "(This is required on MacOS)" refers to the `.pkg` being signed when signing is configured, and I could not read the Code Signing page itself.
- The electron-builder "Auto Update" page did not describe the AppImage replacement algorithm (rename vs write-over), only the `appimage-filename-updated` event.
- Squirrel.Windows release years are not shown on the releases page; "2.0.1" is the last tag but I could not confirm its year from the page.
- I could not fetch Apple's "Updating Mac Software" guidance (page body empty), so the "write to temp then atomically replace" advice is reported only via a search snippet (not quoted here).

## Key question 2 — The "install location" question (per-user vs per-machine)

### Takeaway
All three candidate stacks default to a per-user install on Windows (no UAC for the update), and both Tauri and Velopack have an elevation fallback on macOS/Linux when the binary sits in an admin-owned directory; per-user locations (`%LOCALAPPDATA%`, `~/Applications`, user-owned AppImage path) are the only configuration in which every library updates silently.

### Cited Findings
- Tauri NSIS: "By default the installer will install your application for the current user only" (no Administrator rights, under `%LOCALAPPDATA%`); `perMachine` "requires Administrator privileges"; `both` lets the user choose but "the installer will require Administrator privileges to execute" — [DOC Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/); updater `quiet` mode "only works in user-wide installations or when your app itself already runs with admin privileges" — [DOC Tauri updater guide](https://v2.tauri.app/plugin/updater/)
- Tauri macOS: non-admin user fix in 2.5.0; `PermissionDenied` → AppleScript "with administrator privileges" — [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md); [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Tauri Linux deb/rpm: `pkexec` → `sudo -S` with zenity/kdialog password → plain `sudo` — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- electron-builder NSIS: `perMachine` default `false` ("If `oneClick` is `true` (default): Whether to install per all users (per-machine)"); `oneClick` default `true`; `allowElevation` default `true` for the assisted installer; with `oneClick: false` and `perMachine: false` the installer shows an install-mode page; the NSIS doc page gives no default install directory — [DOC electron-builder NSIS](https://www.electron.build/docs/nsis/); per-machine NSIS updates are skipped by the automatic install because of the UAC prompt; in v27 every per-machine build sets `isAdminRightsRequired` — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- Velopack Windows: `%LocalAppData%\{packId}` by default, Setup.exe "does not require elevation or use privileged directories"; MSI per-machine variant requires elevation — [DOC Velopack Windows](https://docs.velopack.io/packaging/operating-systems/windows); macOS `.pkg` lets the user choose `/Applications` or `~/Applications`; `/Applications` triggers AppleScript elevation — [DOC Velopack macOS](https://docs.velopack.io/packaging/operating-systems/macos); Linux privileged folder → `pkexec` prompt — [DOC Velopack Linux](https://docs.velopack.io/packaging/operating-systems/linux)
- Sparkle: documentation read for this note does not describe the authorization prompt; it only says updates from a read-only mount or under app translocation fail silently by default — [DOC Sparkle documentation](https://sparkle-project.org/documentation/)
- Prism Launcher's updater refuses macOS installs and excludes Flatpak ("should not be affected") — [ISSUE PollyMC commit](https://git.plan9.rocks/fn2006/PollyMC/commit/50d5eb0621b0523db175672a511fd711d4018bac); [ISSUE Prism PR #1268](https://github.com/PrismLauncher/PrismLauncher/pull/1268)

### Inferences
- [INF] A Tauri NSIS `currentUser` install + updater `passive` (default) mode gives a UAC-free Windows update; choosing `quiet` is safe only because the install is per-user. Offering `perMachine`/`both` would re-introduce UAC on every update and, under electron-updater, would disable automatic install entirely.
- [INF] On macOS the documented default target for drag-install is `/Applications`, which for non-admin accounts or for apps dragged there by an admin and run by another user forces the AppleScript password prompt in both Tauri and Velopack; recommending `~/Applications` in the DMG/README avoids it at the cost of being unconventional.
- [INF] The Windows "Program Files" vs "%LOCALAPPDATA%" split is the single biggest determinant of self-update friction for an unsigned app; a per-user install also keeps SmartScreen prompts to the first installer launch only (reported pattern, see winget note above).

### Gaps
- The exact per-user install path for Tauri NSIS (whether `%LOCALAPPDATA%\Programs\<app>` or `%LOCALAPPDATA%\<app>`) is not stated on the fetched docs page; electron-builder's NSIS page likewise gives no default directory.
- I did not find a Sparkle doc page describing the admin-password authorization flow for `/Applications` installs.

## Key question 3 — Security without code signing

### Takeaway
Every viable library already gives you an Ed25519-class signature over the update payload (Tauri: minisign on the artifact; electron-builder v27: Ed25519 on the manifest + SHA-512 per file; Sparkle/WinSparkle: EdDSA on the archive; AppImage: optional `.sha256_sig`) plus HTTPS; this covers a compromised or spoofed update feed/CDN and tampered downloads, but not a compromised CI secret, a stolen signing key, or a malicious first install — and it buys nothing against Gatekeeper/SmartScreen warnings.

### Cited Findings
- Tauri: minisign signature over the whole artifact, verified before install (2.14.0 re-verifies in `install`); trusted-comment `version:` bound to the announced version (2.14.0 for restored updates); HTTPS enforced in release unless `dangerousInsecureTransportProtocol`; non-https download URL logs a warning (2.14.0); `minisign-verify` 0.3 rejects non-canonical `S` (2.13.3); downgrade switch moved out of webview-reachable JS (2.12.0) — [DOC guide](https://v2.tauri.app/plugin/updater/); [DOC CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md); [DOC source](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Tauri key handling in CI: `TAURI_SIGNING_PRIVATE_KEY` (content or path) + optional password env var; ".env files do not work!" — [DOC guide](https://v2.tauri.app/plugin/updater/)
- electron-builder: `files[].sha512` in `latest.yml`; v27 Ed25519-signed manifests that fail closed; "Code signature validation is performed on Windows and macOS"; Linux packages unsigned (`allowUnverifiedLinuxPackages: true`) — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/); [DOC Signed Update Manifests](https://www.electron.build/docs/features/signed-update-manifests/)
- Sparkle: EdDSA mandatory for updates ("you must cryptographically sign your updates"), optional signed feed (`SURequireSignedFeed`, Sparkle 2.9), HTTPS recommended — [DOC Sparkle publishing](https://sparkle-project.org/documentation/publishing/); [DOC Sparkle documentation](https://sparkle-project.org/documentation/)
- Historic bypasses show the verification code itself is the attack surface: electron-updater 2020 RCE via signature-validation bypass — [ISSUE Doyensec](https://blog.doyensec.com/2020/02/24/electron-updater-update-signature-bypass.html); Sparkle CVE-2025-0509 (< 2.6.4) — [ISSUE NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-0509)
- Velopack docs: delta page does not mention hashes or integrity checks for packages — [DOC deltas](https://docs.velopack.io/packaging/deltas)
- OS gatekeeping is unaffected by update-manifest signing: "Both Windows and macOS prevent users from running unsigned applications"; distribution without signing is possible but users must complete "multiple advanced and manual steps" — [DOC Electron code-signing tutorial](https://www.electronjs.org/docs/latest/tutorial/code-signing); Apple forum answer: macOS "won't run unsigned Apple silicon code" (ad-hoc or unsigned-on-Intel runs) — [ISSUE Apple Developer Forums 767774](https://developer.apple.com/forums/thread/767774)
- Homebrew will disable casks failing Gatekeeper checks in September 2026 — [DOC Homebrew 5.0.0](https://brew.sh/2025/11/12/homebrew-5.0.0/)

### Inferences
- [INF] Threat model covered by minisign/Ed25519 manifest + artifact signatures + HTTPS: MITM, a hijacked GitHub Pages site/custom domain, a tampered release asset, a replay of an old version (Tauri's version-bound trusted comment + downgrade block). Not covered: a leaked `TAURI_SIGNING_PRIVATE_KEY` in CI (anyone with repo secrets can sign), a compromised GitHub account that both edits the feed and re-signs, and trojaned first installs (no trust anchor before the pubkey is baked in).
- [INF] "Pinning the GitHub Pages feed" in Tauri is limited to the `endpoints` list with HTTPS; there is no certificate-pinning option in the plugin config read, so TLS trust is the OS trust store.
- [INF] Because Apple Silicon refuses fully unsigned binaries, the macOS build must at least be ad-hoc signed (`codesign -s -`) in CI; that is compatible with Tauri/Velopack updating (no signature-match check) and with Sparkle (EdDSA path), but incompatible with Squirrel.Mac (cdhash requirement).

### Gaps
- I could not find documentation of Velopack's package integrity check (SHA-1/SHA-256 in `releases.{channel}.json`) — the delta page is silent and the Rust source was not fetched.
- No primary source found for Tauri on whether the NSIS installer itself is validated beyond the minisign check (e.g., Authenticode is not consulted) — inferred from the source, which only verifies minisign.

## Key question 4 — Rollback and atomicity

### Takeaway
None of the libraries offers a user-visible "roll back to previous version" button; they differ in how atomic the swap is: Tauri macOS uses an atomic `renamex_np` swap with a two-rename fallback that restores on failure, Tauri Linux AppImage uses move-aside-then-write with restore-on-failure, Tauri Windows delegates everything to the NSIS/MSI installer and exits, Velopack keeps a `current/` directory and relaunches the old version if it cannot swap, and Windows' exe lock is handled by the "rename, don't unlink" trick everywhere.

### Cited Findings
- Tauri macOS: `renamex_np` + `RENAME_SWAP`; fallback `replace_bundle` "does two renames and restores the original on failure"; on failure `keep_backup_if_not_restored` may keep the old app beside the target or in the home folder — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Tauri Linux AppImage: rename current file aside (same device), write new bytes over the target, restore permissions, "If the write fails, it renames the backup back"; backup dir removed on drop after success — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)
- Tauri Windows: installer temp dir is `.keep()`'d (never auto-removed), `std::process::exit(0)` after `ShellExecuteW`; the guide "does not describe general install-failure recovery"; rollback possible only via a dynamic server + custom `version_comparator` sending an older version — [DOC source updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs); [DOC guide](https://v2.tauri.app/plugin/updater/)
- Velopack Windows: whole `current/` dir replaced; if locked, kill processes in `current`, else prompt or abort; if the locker cannot be identified "the old version of the application will be launched" — [DOC Velopack Windows](https://docs.velopack.io/packaging/operating-systems/windows); macOS bundle "extracted and replaced in place", app "can update while running", Velopack "tries to close and restart it" — [DOC Velopack macOS](https://docs.velopack.io/packaging/operating-systems/macos)
- electron-updater: to pull a bad release "publish a higher version number. Re-publishing the same version does not reach users who already got the broken one"; staged rollouts via `stagingPercentage` — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- Windows exe-lock semantics (reference implementation, `self-replace` 1.5.1): "when an executable launches it can be renamed, but it cannot be unlinked"; the crate moves the running exe aside, copies itself with `FILE_FLAG_DELETE_ON_CLOSE`, waits for the parent to exit, deletes it; `MOVEFILE_DELAY_UNTIL_REBOOT` rejected as privileged; power loss can leave dot-prefixed temp files; on Unix "the file is just unlinked" and replacement is "an atomic move with `rename`" — [DOC docs.rs self-replace](https://docs.rs/self-replace/latest/self_replace/)
- Prism Launcher's custom Windows updater: extract to temp, write a marker with the install path, run the new updater, exit; new updater moves files in, copies itself over the old updater; removed files are backed up by moving; next start "sees marker files, present user with update log and cleans up"; the author's claim "if there is an error there is still an intact launcher install" is marked presumptive in the PR — [ISSUE Prism PR #1268](https://github.com/PrismLauncher/PrismLauncher/pull/1268)
- Reported failure mode on signed apps after in-place update: Cursor 3.6.31 "Electron Framework code signature invalidated after auto-update" — [ISSUE Cursor forum](https://forum.cursor.com/t/bug-report-cursor-3-6-31-crashes-on-launch-electron-framework-code-signature-invalidated-after-auto-update/162274); Tor Browser: "all components of the macOS version of Tor Browser will become unsigned after an in-app update" — [ISSUE Tor #40754](https://gitlab.torproject.org/tpo/applications/tor-browser/-/issues/40754)

### Inferences
- [INF] For a one-window manager, the cheapest robust rollback is "keep the previous artifact next to the app and offer Reinstall previous" implemented by the app itself; none of the libraries will do it, and Tauri's downgrade path requires a dynamic server rather than a static `latest.json`.
- [INF] Tauri Windows atomicity is exactly NSIS's atomicity: the installer overwrites files in `%LOCALAPPDATA%` after the app exits; a crash mid-install leaves a half-written tree, which is the same risk any NSIS-based updater (electron-updater included) carries.
- [INF] The in-place-seal problems reported for Cursor and Tor Browser are specific to code-signed bundles; an unsigned/ad-hoc bundle has no seal to break, so the failure class does not apply here.

### Gaps
- No source describes what Tauri's NSIS `/UPDATE` flag does inside the generated installer (e.g. skip shortcuts, keep settings); the updater source only passes it.
- No official Velopack rollback documentation was found.

## Key question 5 — Manager self-update vs updates of the managed plugins; prior art

### Takeaway
Prior art splits the two: Modrinth App uses tauri-plugin-updater for itself (own CDN `updates.json`, Windows `quiet` mode, `v1Compatible` artifacts) while plugin/modpack content flows through its own API; JetBrains Toolbox updates IDEs by patch sequences and itself separately; Prism Launcher wrote a custom GitHub-Releases updater for Windows/Linux and relies on Sparkle on macOS.

### Cited Findings
- Modrinth App (Tauri) `tauri-release.conf.json`: `plugins.updater.endpoints = ["https://launcher-files.modrinth.com/updates.json"]`, minisign `pubkey`, `windows.installMode: "quiet"`, `bundle.createUpdaterArtifacts: "v1Compatible"` — [DOC modrinth/code tauri-release.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri-release.conf.json); base `tauri.conf.json`: NSIS `installMode: "currentUser"`, `installerHooks: ./nsis/hooks.nsi`, macOS `signingIdentity: null` in the base file — [DOC tauri.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri.conf.json); `tauri-plugin-updater` is a dependency (optional on the Linux target) — [DOC Cargo.toml](https://raw.githubusercontent.com/modrinth/code/main/apps/app/Cargo.toml); the app is "the Tauri-based launcher" with a Rust backend and Vue frontend — [DOC Modrinth docs](https://docs.modrinth.com/contributing/theseus/); changelog fixes "the updater restarting the app without being asked" and the app reopening after a pending update — [ISSUE Modrinth changelog](https://modrinth.com/news/changelog?filter=app)
- Prism Launcher 8.0: "Implement updater for Windows and Linux" (#1268, #1721), "Allow disabling bundling and Sparkle updater when building" — [DOC Prism 8.0 release](https://github.com/PrismLauncher/PrismLauncher/releases/tag/8.0); plan: "Pull release info from the github api", pick the asset by architecture and install type, portable vs installer paths, "attempt to call embedded `AppImageUpdate`" on Linux; Flatpak unaffected; merged 2023-10-16 — [ISSUE PR #1268](https://github.com/PrismLauncher/PrismLauncher/pull/1268); macOS: updater refuses with a message that it does not support macOS installs — [ISSUE PollyMC commit](https://git.plan9.rocks/fn2006/PollyMC/commit/50d5eb0621b0523db175672a511fd711d4018bac); Prism 8.2 added macOS code signing and notarization — [ISSUE tech-insider](https://tech-insider.org/prism-launcher-setup-2026/)
- JetBrains Toolbox: "Toolbox automatically chooses to download and apply a patch (or even a sequence of patches) instead of the full package download"; installing an IDE via Toolbox "disables the IDE's built-in update checker"; Toolbox self-update "now enabled by default"; current version 3.9 (19 Oct 2026) — [DOC JetBrains Toolbox](https://www.jetbrains.com/toolbox/app/); [DOC Rider help](https://jetbrains.com/help/rider/2021.1/Update.html)
- electron-updater and Tauri both let the app fetch arbitrary other feeds; Tauri's updater is scoped to the app's own target/platform keys — [DOC Tauri guide](https://v2.tauri.app/plugin/updater/)

### Inferences
- [INF] Keep two manifests: `latest.json` in Tauri's exact schema for the manager (so the stock plugin can consume it), and a separate plugin catalogue JSON (per-plugin version, per-OS URL, SHA-256, minisign signature, install path hints) that the manager itself parses — mixing them would force the plugin catalogue into Tauri's `platforms.{os-arch}` single-artifact shape, which cannot express several plugins.
- [INF] Reusing the same minisign key pair for the plugin catalogue is defensible (one secret in CI), but signing each plugin bundle with the same `tauri signer` tool means the catalogue signature format equals the manager's, which is convenient for a Rust `minisign-verify` call in the manager.
- [INF] Modrinth's choice of `quiet` on Windows is only safe because its NSIS install is `currentUser`; Krate should mirror that pairing or stay on `passive`.

### Gaps
- How JetBrains Toolbox replaces its own binary per OS was not described in any fetched source.
- I did not verify whether Modrinth's `tauri.macos.conf.json` sets a signing identity (the base file sets `null`), so I cannot say whether its macOS updates run unsigned.

## Key question 6 — GitHub as the update backend

### Takeaway
Unauthenticated `api.github.com` calls are capped at 60/hour per IP (shared NAT = shared quota), so the manager should never poll the REST API; the stable `https://github.com/<owner>/<repo>/releases/latest/download/<asset>` redirect and a static `latest.json` on GitHub Pages (publishes in up to 10 minutes, 100 GB/month soft bandwidth) are both unlimited for practical purposes, and "latest" means the most recent non-prerelease, non-draft release ordered by the commit's `created_at`.

### Cited Findings
- "The primary rate limit for unauthenticated requests is 60 requests per hour", tied to the originating IP; authenticated PAT/OAuth 5,000/h; `GITHUB_TOKEN` in Actions 1,000/h per repo; secondary limits: ≤100 concurrent, ≤900 REST points/min; headers `x-ratelimit-limit/remaining/used/reset/resource` — [DOC GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- Velopack's `GithubSource` documents the same consequence: without `access_token` requests are "rate limited to 60 req/hr per IP" — [DOC docs.rs GithubSource](https://docs.rs/velopack/latest/velopack/sources/struct.GithubSource.html); electron-updater's GitHub provider avoids the API for public repos and only uses it with `GH_TOKEN` for private ones — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- Stable asset URL: append `/releases/latest/download/asset-name.zip` to the repo URL for an asset "that was manually uploaded"; `releases/latest` gives the latest release page — [DOC GitHub linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)
- "The latest release is the most recent non-prerelease, non-draft release, sorted by the created_at attribute. The created_at attribute is the date of the commit used for the release, and not the date when the release was drafted or published." — [DOC GitHub REST releases](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28)
- GitHub Pages: "It can take up to 10 minutes for changes to your site to publish after you push the changes to GitHub." — [DOC creating a Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site); "soft bandwidth limit of 100 GB per month", "soft limit of 10 builds per hour" (not with a custom Actions workflow), sites "no larger than 1 GB", deployments time out after 10 minutes; not allowed "as a free web-hosting service to run your online business" or SaaS — [DOC GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- Pages CDN caching (secondary sources only): `Cache-Control: max-age=600` observed on Pages assets — [ISSUE Stack Overflow mirror 2013](https://dev.library.kiwix.org/content/stackoverflow_en_nopic_2021-08/questions/14798589/github-pages-http-headers); custom `Cache-Control` headers are not supported on Pages — [ISSUE jquery.app tool page](https://www.jquery.app/tools/cache-control-header-builder/); raw.githubusercontent stale reads attributed to CDN caching, with some repos showing `max-age=86400` — [ISSUE GitHub community #46691](https://github.com/orgs/community/discussions/46691)
- AppImage `gh-releases-zsync|user|repo|latest|pattern` resolves "latest" while ignoring pre-releases — [DOC AppImageSpec](https://github.com/AppImage/AppImageSpec/blob/master/draft.md)

### Inferences
- [INF] A Tauri `endpoints` list of `["https://<owner>.github.io/<repo>/latest.json", "https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]` gives a 10-minute-cached primary and a redirect-based fallback; Tauri only fails over on non-2XX, so a stale-but-valid Pages copy will be used as-is for up to ~10 minutes after a release — acceptable for a plugin manager.
- [INF] Because "latest" is ordered by the release commit's `created_at`, a hotfix tagged on an older commit can be out-ordered; releasing from the tip of main avoids the surprise.
- [INF] The GitHub Pages ToS wording bars commercial SaaS, not a static update feed for a free, open-source installer; a static `latest.json` plus a plugin catalogue is within the documented limits by orders of magnitude.

### Gaps
- GitHub does not publish an official document stating the Pages `max-age=600`; the figure rests on observed headers in third-party sources.
- Whether `/releases/latest/download/<asset>` itself is cached or always redirects live was not documented on the fetched page.

## Key question 7 — Recommendation for an unsigned Tauri / Electron / C++ app

### Takeaway
Use **Tauri 2 + tauri-plugin-updater (≥ 2.14.1)** with NSIS `installMode: currentUser`, updater `installMode: passive`, `createUpdaterArtifacts: true`, an ad-hoc-signed macOS `.app.tar.gz`, AppImage on Linux (deb/rpm optional via `pkexec`), minisign key in CI via `TAURI_SIGNING_PRIVATE_KEY`, a static `latest.json` on GitHub Pages with a `/releases/latest/download/` fallback endpoint, and a separate signed plugin-catalogue JSON parsed by the manager. Electron is excluded by the Squirrel.Mac signing requirement; Velopack is the fallback if the app is written in C++ (Qt) instead of Tauri.

### Cited Findings
- Tauri fits all three platform constraints without platform signing: minisign-only verification, `renamex_np` swap on macOS with AppleScript elevation fallback, AppImage/deb/rpm on Linux, NSIS/MSI on Windows with per-user default — [DOC guide](https://v2.tauri.app/plugin/updater/); [DOC source](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs); [DOC Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- Electron excluded: "macOS application must be signed in order for auto updating to work." — [DOC Auto Update](https://www.electron.build/docs/features/auto-update/)
- Velopack as the C++ alternative: cross-platform, C++ binding shipped as a pre-compiled lib, per-user `%LocalAppData%`, in-place macOS replacement, AppImage with `pkexec` fallback, Zstandard deltas; `GithubSource` warns about the 60 req/h cap so a static URL source is preferable — [DOC C++](https://docs.velopack.io/getting-started/cpp); [DOC Windows](https://docs.velopack.io/packaging/operating-systems/windows); [DOC macOS](https://docs.velopack.io/packaging/operating-systems/macos); [DOC Linux](https://docs.velopack.io/packaging/operating-systems/linux); [DOC deltas](https://docs.velopack.io/packaging/deltas); [DOC GithubSource](https://docs.rs/velopack/latest/velopack/sources/struct.GithubSource.html)
- Modrinth App demonstrates the Tauri recipe in production (static `updates.json`, `currentUser` NSIS, `quiet` updater) — [DOC tauri-release.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri-release.conf.json); [DOC tauri.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri.conf.json)
- Package-manager route is closing on macOS for unsigned apps (Homebrew disabling Gatekeeper-failing casks in September 2026) — [DOC Homebrew 5.0.0](https://brew.sh/2025/11/12/homebrew-5.0.0/)

### Inferences
- [INF] Concrete Tauri configuration: `bundle.windows.nsis.installMode: "currentUser"`; `plugins.updater.windows.installMode: "passive"` (switch to `"quiet"` only if the UI already told the user an update is installing); `plugins.updater.endpoints` = Pages URL then `/releases/latest/download/latest.json`; `createUpdaterArtifacts: true` (not `v1Compatible`, which goes away in v3); after `downloadAndInstall()` call `relaunch()` on macOS/Linux, and on Windows rely on `restartAfterInstall` (2.11.0+).
- [INF] macOS: `codesign --force --deep -s - Krate\ Manager.app` in CI before `tar.gz`, document that first launch needs right-click → Open (or `xattr -d com.apple.quarantine`), and tell users to drop it in `~/Applications` to avoid the admin prompt on every update.
- [INF] Rollback: keep the last downloaded artifact in the app data dir and expose "Reinstall previous version" by feeding it back through the same minisign check (Tauri's `restore_update` path enforces the version-bound signature); do not rely on a dynamic server.
- [INF] Plugin updates: a separate `plugins.json` (per plugin: version, per-OS URL on `/releases/latest/download/`, SHA-256, minisign signature made with the same key via `tauri signer sign`) that the manager verifies with `minisign-verify` before writing into the VST3/AU folders; this keeps one key, one tool, two schemas.

### Gaps
- Not measured: actual UAC behaviour of Tauri's NSIS `/P /UPDATE` on a `currentUser` install when the previous install was `perMachine` (mode mismatch) — no source found.
- Not verified on hardware: whether a non-ad-hoc-signed (fully unsigned) Tauri `.app.tar.gz` even launches on Apple Silicon after a swap; Apple forum guidance says unsigned arm64 code is refused, so ad-hoc signing in CI is a must — but no Tauri-specific report was found.
