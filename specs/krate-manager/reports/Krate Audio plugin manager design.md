# Build Krate Manager on Tauri, Place Files Yourself

Krate Audio should build the plugin manager on **Tauri 2** and have it **extract plain bundle archives into the plug-in folders itself** rather than drive the Inno Setup / `.pkg` installers, because Tauri is the only candidate whose first-party self-updater is documented to work on Windows, macOS and Linux with nothing but its own minisign key pair, and because a manager that writes the bytes itself is, under a never-sign policy, a *better* install path than any installer a browser downloads. Electron is disqualified by its own documentation ("macOS application must be signed in order for auto updating to work"), Velopack says notarization is "required", Wails v3 shipped three days before this research, and Qt has no updater plus LGPL and commercial-first LTS obligations. The install strategy follows from the no-certificate constraint: on macOS, files written by a non-browser process carry no `com.apple.quarantine` attribute, so bundles the manager extracts load in every DAW without the "Open Anyway" dance that quarantined, unsigned VST3s can never pass; on Linux there is no installer today, so the manager must place files anyway; on Windows the only asymmetry is that the spec-blessed per-user VST3 folder is "mainly for development use", so the default stays `C:\Program Files\Common Files\VST3` behind one UAC prompt from a tiny elevated sidecar. The release feed needs three additive changes (a `schema_version: 2` `versions.json` that keeps the three keys nine shipped plugins already parse, a per-release `release.json`, and a Tauri-shaped `manager/latest.json`), one new artifact per OS (a plain `.zip`/`.tar.gz` beside each installer), SHA-256 plus minisign signatures generated in CI, and two new workflows (`release-manager.yml`, `feed.yml`). The hard consequence of "no certificates ever" is **one unavoidable prompt per fresh download** (SmartScreen "Run anyway", Gatekeeper "Open Anyway", or a hard block under Windows 11 Smart App Control) and a mandatory ad-hoc `codesign -s -` on every Mach-O, because Apple Silicon refuses completely unsigned code outright; everything after that first launch, including self-update and every plugin install, can be prompt-free if the design below is followed.

## Tauri 2 is the only stack whose updater ships unsigned on all three OSes

The framework question reduces to a single filter: which stack can replace its own binary on a Mac with no Apple identity. Electron fails that filter in its own words. The Electron `autoUpdater` docs state "Your application must be signed for automatic updates on macOS. This is a requirement of Squirrel.Mac" ([Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)), and electron-builder repeats "macOS application must be signed in order for auto updating to work" ([electron-builder auto-update](https://www.electron.build/docs/features/auto-update)). Ad-hoc signing does not rescue it: electron-builder's `identity: "-"` produces a signature that "will only run on the machine that built it" ([electron-builder mac target](https://www.electron.build/docs/mac/)), and one project found the ad-hoc designated requirement is the `cdhash` of that one build, so no later release can satisfy Squirrel.Mac ([plasma PR #41](https://github.com/pankajyadav05/plasma/pull/41)). Velopack, the natural updater for an Avalonia or C++ app, says "Code signing and notarization is required by Apple before shipping your releases to users, or your app won't run" ([Velopack macOS](https://docs.velopack.io/packaging/operating-systems/macos)). Wails v3.0.0 was published on **2026-10-26** with an in-app updater and a GitHub Releases provider, but whether that updater needs Apple signing is not stated and no production report exists ([Wails v3.0.0 notes](https://api.github.com/repos/wailsapp/wails/releases/tags/v3.0.0)). Qt 6.12 LTS is the strongest non-webview option for a C++ team, but it ships no in-app updater (Qt Installer Framework is an installer, not an updater), requires LGPLv3 relinking and source-delivery hygiene, and locks LTS patch releases to commercial customers ("immediate access to LTS releases is limited to commercial customers") ([Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations); [Qt Releases](https://doc.qt.io/qt-6/qt-releases.html)).

Tauri passes the filter by construction. Its updater "needs a signature to verify that the update is from a trusted source. Signing cannot be turned off", the key pair comes from `tauri signer generate`, and the page never requires an Apple or Microsoft certificate ([Tauri updater plugin](https://v2.tauri.app/plugin/updater/)). The plugin's source shows why it works unsigned: verification is minisign over the package bytes; on macOS it extracts the `.app.tar.gz` and swaps the bundle with `renamex_np(RENAME_SWAP)`, falling back to `do shell script ... with administrator privileges` on `PermissionDenied`, with no `codesign` or quarantine handling anywhere; on Windows it launches the downloaded NSIS installer with `ShellExecuteW` verb `"open"` and `/UPDATE /P`; on Linux it overwrites the AppImage in place or runs `pkexec dpkg -i` / `pkexec rpm -U` ([updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs)). Note that Tauri's Linux updater is no longer AppImage-only: the changelog records "Added support for `.deb` package updates" in 2.1.0 and "supports all bundle types: Deb, Rpm and AppImage" in 2.10.0 ([updater CHANGELOG](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/CHANGELOG.md)). The latest release is **updater 2.14.1 (2026-10-28)** with 13.5 M downloads, and every plugin the manager needs (`http`, `fs`, `shell`, `process`, `dialog`, `store`, `upload`, `log`, `single-instance`) had an October 2026 release ([crates.io](https://crates.io/api/v1/crates?q=tauri-plugin&per_page=50&sort=downloads)). Modrinth App proves the recipe in production: a Tauri shell, Rust core, Vue frontend, `tauri-plugin-updater` against a static `updates.json`, NSIS `installMode: "currentUser"` ([Modrinth tauri.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri.conf.json); [tauri-release.conf.json](https://raw.githubusercontent.com/modrinth/code/main/apps/app/tauri-release.conf.json)).

The size argument is real and matters for a tool that sits beside nine plugins. A six-month Tauri production report measured installers at **12 MB (Windows), 18 MB (macOS .dmg) and 17 MB (.deb)** against 201, 290 and 207 MB for a comparable Electron app ([HackerNoon: Six months with Tauri](https://hackernoon.com/six-months-with-tauri-the-benefits-and-the-bill)). The audio industry's own managers show the Electron tax at scale: Native Access 574 MB, Waves Central 826 MB, Softube Central 875 MB, versus Arturia Software Center (Qt) 80 MB and Spitfire (JUCE) 86 MB ([Desktop Insights: Native Access](https://desktopinsights.com/apps/native-access); [Waves Central](https://desktopinsights.com/apps/waves-central); [Softube Central](https://desktopinsights.com/apps/softube-central); [Arturia Software Center](https://desktopinsights.com/apps/arturia-software-center)), and Waves users complain of "major 250mb updates every month or two" ([Trustpilot: Waves](https://ca.trustpilot.com/review/waves.com?page=7)).

| Candidate | Self-update without Apple/MS certificate | Installer size class | Main cost for Krate |
|---|---|---|---|
| **Tauri 2** | Yes, documented and visible in source (minisign only) | 5-18 MB; Linux AppImage 70-94 MB | WebKitGTK NVIDIA/Wayland seams; capability JSON; some Rust |
| Electron | No on macOS (Squirrel.Mac requires signing) | 200-290 MB | Fails the hard constraint |
| Qt 6 C++ | No first-party updater at all | ~80 MB | Write updater yourself; LGPL relinking; LTS paywall |
| Avalonia + Velopack | Velopack: macOS notarization "required" | n/a | Fails the hard constraint |
| Wails v3 | Unknown (released 2026-10-26) | similar to Tauri | Go toolchain; zero production history |
| iced / egui / Slint / Dioxus | No updater story; Dioxus desktop is a webview anyway | small | Everything in Rust; fewer widgets |

The bill for Tauri is Linux. Tauri 2 hard-requires WebKitGTK 4.1, and the documented failure class is NVIDIA plus the WebKitGTK DMABUF renderer: blank or white windows, flicker, `Error 71 (Protocol error) dispatching to Wayland display`, with a four-step workaround ladder ending in `WEBKIT_DISABLE_DMABUF_RENDERER=1` that the docs warn not to ship unconditionally ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)). Shipping Tauri apps such as Yaak publish the same workaround page for their users ([Yaak](https://yaak.app/docs/getting-started/linux-graphics-issues)). The AppImage bundles WebKitGTK from the build host, which is why Tauri says to build on "the oldest base system you intend to support", naming Ubuntu 22.04 and Debian 12, and why it grows "to 70+ MB" ([Tauri AppImage](https://v2.tauri.app/distribute/appimage/)); a truly portable AppImage bundler is still a draft PR ([tauri PR #12491](https://github.com/tauri-apps/tauri/pull/12491)). The pragmatic Linux answer is `.deb` + `.rpm` as the primary formats (system WebKit, 2-6 MB) with the AppImage built on `ubuntu-22.04` as the fallback, and the NVIDIA toggle exposed as a setting or gated on a detected `nvidia` module. The Rust footprint for a C++ team is modest but not zero: downloads with progress and resume, SHA-256, archive extraction, plugin-folder scanning and the privileged copy all belong in `#[tauri::command]` functions rather than behind JS-facing plugin scopes (the alternative is granting the webview write access to `/Library/Audio/Plug-Ins/**`), which the feasibility note estimates at **1,200-2,000 lines of Rust plus a 200-400-line helper CLI**, with the UI in ordinary Vite + TypeScript scaffolded by `create-tauri-app` ([Tauri: Create a Project](https://v2.tauri.app/start/create-project/); [Calling Rust from the Frontend](https://v2.tauri.app/develop/calling-rust/)). A Node.js CLI that consumes the same feed should exist regardless, for CI and for users whose webview is broken.

## Detect through moduleinfo.json, install by extracting archives, elevate one sidecar once

Detection needs no plugin loading on any OS. Steinberg specifies the search folders in priority order (user first, then global), says VST3 "doesn't require a plug-in registration", and allows symlinks ([Steinberg: Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html)). Every SDK-3.7.5+ bundle carries `Contents/Resources/moduleinfo.json` with a top-level `Version` and per-class `Version` strings ([Steinberg: Plug-in Format](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Format.html); [moduleinfo.h](https://github.com/steinbergmedia/vst3_public_sdk/blob/master/source/vst/moduleinfo/moduleinfo.h)). Two repo facts shape the parser. First, the installed Membrum bundle on this machine (`C:\Users\scab\AppData\Local\Programs\Common\VST3\Membrum.vst3\Contents\Resources\moduleinfo.json`) uses JSON5-style trailing commas, so a strict JSON parser rejects it. Second, that same file has top-level `Version` `0.8.0` but class `Version` `0.12.2.1`: the Krate build does not keep the two in sync, and the manager must pick one (the class version is the one that tracks `version.json`) and the build should be fixed to emit both identically before the manager ships, or it will report phantom updates of exactly the kind users punish in KVR Studio Manager and Cherry Audio Sync ([KVR forum](https://www.kvraudio.com/forum/viewtopic.php?p=8868766); [KVR thread](https://www.kvraudio.com/forum/viewtopic.php?p=9182325)). For the AU, `Contents/Info.plist` holds `CFBundleShortVersionString` and the `AudioComponents[].version` integer ([Apple TN2276](https://developer.apple.com/library/archive/technotes/tn2276/_index.html)). Legacy installs are detectable too: Krate's Inno script uses `PrivilegesRequired=admin` and `ArchitecturesInstallIn64BitMode`, so its uninstall entry is `HKLM\...\Uninstall\{8F7C4A2B-...}_is1` in the 64-bit registry view (`F:\projects\iterum\plugins\iterum\installers\windows\setup.iss`; [Inno: AppId](https://jrsoftware.org/ishelp/topic_setup_appid.htm); [Inno: 32-bit vs 64-bit](https://jrsoftware.org/ishelp/topic_32vs64bitinstalls.htm)), and the macOS `pkgbuild --identifier com.krateaudio.<name>` leaves a `pkgutil` receipt with `version` and a `--files` list (`F:\projects\iterum\.github\workflows\release.yml`; [pkgutil(1)](https://keith.github.io/xcode-man-pages/pkgutil.1.html)).

Driving the existing installers (Strategy A) is complete on Windows and broken on the other two platforms, which is the decisive argument against it. Inno Setup gives a full silent lifecycle: `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /LOG="file"`, exit codes 0-8, and an uninstaller that takes the same switches, with the caveat that the uninstaller "copies itself to TEMP" and returns its exit code before the original is gone, so the manager must poll for the `.vst3` folder's disappearance ([Inno: Setup command line](https://jrsoftware.org/ishelp/topic_setupcmdline.htm); [Setup exit codes](https://jrsoftware.org/ishelp/topic_setupexitcodes.htm); [Uninstaller exit codes](https://jrsoftware.org/ishelp/topic_uninstexitcodes.htm)). On macOS, "The installer command requires root privileges to run" and "the macOS installation system does not have an option to uninstall or remove files and apps installed from a package" ([installer(8)](https://keith.github.io/xcode-man-pages/installer.8.html); [Scripting OS X](https://scriptingosx.com/2025/07/inspecting-packages/)). On Linux, Krate ships only a `tar.gz` with no install script at all (`release.yml`, `linux-archive` job). So Strategy A would mean three different code paths, root for every macOS install, and a manager-implemented uninstall on macOS regardless. Strategy B (the manager stages, verifies, extracts and copies) is one code path on all three OSes, and every surveyed launcher-class tool (Modrinth, Prism) works this way: download plain files, verify hashes, place them ([Modrinth modpack format](https://docs.modrinth.com/modpacks/format)).

The per-user folders remove elevation entirely on macOS and Linux, and almost on Windows. Apple names `~/Library/Audio/Plug-Ins/Components/` as a normal install location ("It is up to you which of these locations you use") ([Apple AU Programming Guide](https://developer.apple.com/library/archive/documentation/MusicAudio/Conceptual/AudioUnitProgrammingGuide/AudioUnitDevelopmentFundamentals/AudioUnitDevelopmentFundamentals.html)); `$HOME/.vst3/` is Steinberg's first-priority Linux folder, Ardour's hard-coded default, where u-he installs, and the only place a Flatpak Bitwig can see since "anything installed in /usr/lib won't be available to Bitwig Studio" ([Ardour forum](https://discourse.ardour.org/t/how-to-properly-load-vst3-on-linux/105022); [u-he Linux paths](https://u-he.com/support/faq/compatibility/install-paths-linux/); [Bitwig support](https://www.bitwig.com/support/technical_support/52/)). Windows is the exception: `%LOCALAPPDATA%\Programs\Common\VST3` is Steinberg's priority-1 folder but is labelled "mainly used for development use case" ([Steinberg: Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html)); the SDK host and JUCE hosts scan it, but JUCE said in 2022 the folder "is not yet well-supported by DAWs" ([JUCE forum](https://forum.juce.com/t/getdefaultlocationstosearch-should-include-localappdata-for-vst3-plugin-scan-path/49735)), Ableton exposes only the system folder plus one custom folder ([Ableton forum](https://forum.ableton.com/viewtopic.php?p=1817700)), and FL Studio, Cubase and Studio One are unconfirmed or reported as fixed to `Program Files\Common Files\VST3` ([Steinberg forums](https://forums.steinberg.net/t/vst-plugin-locations-in-cubase-9-5-vs-earlier-gens/130798/4); [Vital forum](https://forum.vital.audio/t/studio-one-5-not-seeing-vital-1-5-vst/11073)). Until a per-DAW test says otherwise, the Windows default must remain `C:\Program Files\Common Files\VST3`, with the per-user folder as an opt-in.

That leaves one elevation on Windows (and an opt-in one on macOS/Linux for users who want `/Library` or `/usr/local/lib/vst3`), which should be designed as a single call to a small sidecar helper rather than a persistent service. There is no Tauri API for elevation and no cross-platform crate that is both mature and captures output (`runas` 1.2.0 "does not support capturing output" ([docs.rs/runas](https://docs.rs/runas))), but the three idioms are exactly the ones Tauri's own updater uses: a UAC prompt on Windows, `osascript ... with administrator privileges` on macOS, `pkexec` with a zenity/kdialog `sudo -S` fallback on Linux ([updater.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs)). The helper ships as a Tauri sidecar (`bundle.externalBin`, allow-listed args) ([Tauri: Embedding External Binaries](https://v2.tauri.app/develop/sidecar/)), takes a JSON job of already-verified staged paths, and does only the final copy, rename or remove as root; staging, hash and signature checks and unpacking run as the user. Apple DTS is explicit that the AppleScript route is "equivalent to `sudo`", not API, and that the supported alternatives (`SMJobBless` / `SMAppService`) need an Apple-issued identity ("if you are using ad hoc signing ... you will see problems like this") ([Apple forums 701118](https://developer.apple.com/forums/thread/701118); [Apple forums 799910](https://developer.apple.com/forums/thread/799910)), so for Krate the sudo-equivalent is the only door. The signed-helper route is also the one that generates the most support traffic in the industry: Native Instruments' privileged NTK Daemon has its own "Please grant permission to NTK Daemon" article whose fix is reinstalling the daemon as Administrator ([NI support](https://support.native-instruments.com/support/solutions/articles/69000879287-native-access-error-please-grant-permission-to-ntk-daemon-to-install-dependencies-)), while Cherry Audio advertises that Sync "does not run as a background service" and "reduces the number of system login or password prompts" by batching ([Cherry Audio: Sync](https://cherryaudio.com/products/sync)). The same single helper call should carry the factory presets, which today go to `C:\ProgramData\Krate Audio\<Plugin>` and `/Library/Application Support/Krate Audio/<Plugin>` (`setup.iss` line 77; `release.yml`), both admin-only paths.

Three mechanics round out Strategy B. Windows lets a loaded DLL be replaced without a reboot: rename it with `MoveFileEx` on the same volume, copy the new one in, and schedule the old name for deletion ([Microsoft: Dynamic-Link Library Updates](https://learn.microsoft.com/en-us/windows/win32/Dlls/dynamic-link-library-updates)); the delayed delete needs admin, so a non-elevated path should leave the renamed file and clean it on the next run. Uninstall should be driven by a manifest of exactly the paths the manager extracted (the Scoop/Homebrew model), with a two-level choice, "Remove plugin" versus "Remove everything including presets", mirroring Homebrew's `zap` rule that it "should not remove files the user created directly" ([Homebrew Cask Cookbook](https://docs.brew.sh/Cask-Cookbook)); legacy installs are removed through the Inno uninstaller or `pkgutil --files` plus `--forget`. Because Steinberg hosts take the "First found plug-in (for a given Processor UID)", a stale copy in the global folder would shadow a fresh per-user install, so migrating a legacy admin install into a per-user folder is a two-step job (remove old, then extract new) and needs the elevation once. Finally, AU pickup after a copy is not deterministic: Apple's documented recovery ladder is restart, Logic's "Reset & Rescan Selection", "Full Audio Unit Reset", then moving `~/Library/Caches/AudioUnitCache` out ([Apple Support 122179](https://support.apple.com/en-us/122179)), while the community `killall -9 AudioComponentRegistrar` works for some installers and "doesn't do the trick anymore these days" for others ([JUCE forum 26753](https://forum.juce.com/t/installing-new-audio-units-requires-restart-in-high-sierra/26753?page=3); [JUCE forum 66963](https://forum.juce.com/t/plugin-manager/66963)); the manager should run the `killall` with its exit code ignored and show Apple's steps in a post-install notice. Do not Flatpak the manager: `/usr` is a reserved path that `--filesystem` cannot grant, and a sandboxed manager could reach `~/.vst3` only with an explicit grant while remaining invisible to Flatpak DAWs, which discover plugins through the `org.freedesktop.LinuxAudio.Plugins` extension instead ([Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html); [flathub BaseExtension](https://github.com/flathub/org.freedesktop.LinuxAudio.BaseExtension)).

## No certificate costs one prompt per fresh download, and nothing after it

On macOS the rules tightened twice and the manager's design must respect both. Sequoia removed the Control-click "Open" bypass; Apple's current guide gives only the path System Settings > Privacy & Security > "Open Anyway", notes the button "is available for about an hour after you try to open the app", and warns that overriding "is the most common way that a Mac gets infected with malware" ([Apple Support: Open a Mac app from an unknown developer](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac); [AppleInsider](https://appleinsider.com/inside/macos-sequoia/tips/whats-changed-in-runtime-protection-for-macos-sequoia)). A Tahoe 26.6.1 test from August 2026 then fixed the floor: an **ad-hoc-signed and quarantined** app is offered to the Trash by default and runs only after the user enables "Anywhere"; an **ad-hoc-signed, not quarantined** app "launched normally, without any warning dialog"; a **completely unsigned** arm64 binary is blocked in every condition because "completely unsigned code has never been allowed in Apple silicon Macs" ([Eclectic Light, 2026-08-11](https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/)). Two consequences follow. CI must `codesign --force --deep -s -` every Mach-O (each VST3, AU, the manager, the helper) **after** the last modifying step (strip, lipo, rpath edits), or Apple Silicon users get a silent kill ([LLVM Discourse](https://discourse.llvm.org/t/ad-hoc-code-signature-anomaly-on-arm64-macos/57628)); Krate's CI currently builds with `SMTG_DISABLE_CODE_SIGNING=ON` and has no codesign step (`F:\projects\iterum\.github\workflows\ci.yml` line 600; `release.yml`), so this is a required pipeline change independent of the manager. And `spctl --master-disable` is no longer advice worth giving: on Tahoe it "doesn't disable Gatekeeper or on-demand XProtect, but merely enables you to run signed apps that haven't been notarised" ([Eclectic Light, 2026-08-06](https://eclecticlight.co/2026/08/06/can-you-disable-gatekeeper-and-xprotect/)).

The quarantine attribute, not the signature, is the lever Krate controls. Quarantine is opt-in per writing process: a file gets `com.apple.quarantine` only if the writing app sets `LSFileQuarantineEnabled=true` in its Info.plist, is listed in Apple's CoreTypes exceptions, or sets the attribute explicitly; `curl` is exempt and curl-downloaded archives "don't gain the xattr when extracted from archives either" ([Eclectic Light, Who decides to quarantine files?](https://eclecticlight.co/2025/12/08/who-decides-to-quarantine-files/)); Apple DTS calls quarantine "typically an opt-in system, so programs that download things have to explicitly set it" ([Apple forums 730314](https://developer.apple.com/forums/thread/730314)). This matters more for plug-ins than for apps: Apple states that "in macOS 10.15 and later, apps can load quarantined plug-ins only if the plug-in is notarized" ([Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)), and testers confirm "'Open anyway' is only for applications" and "no longer works for dynamic libraries" ([JUCE forum 64574](https://forum.juce.com/t/mac-open-anyway-not-working-for-unsigned-mac-vst3/64574)). A quarantined, unsigned Krate VST3 therefore has no user-facing escape short of `xattr -rd com.apple.quarantine`, which is exactly what KVR and HISE threads tell people to run ([KVR](https://www.kvraudio.com/forum/viewtopic.php?p=8948902); [HISE forum](https://forum.hise.audio/post/96762)). The current `.pkg` route works because "macOS will not place binaries installed from a pkg under quarantine", which is why DISTRHO ships Cardinal as an unsigned pkg with a two-sentence note ([Cardinal wiki](https://github.com/DISTRHO/Cardinal/wiki/Install)). A Tauri manager that downloads with `reqwest` and extracts with its own tar/zip code writes plug-in bundles, and its own replacement `.app`, with no quarantine attribute, so a DAW never assesses them and a self-update never re-triggers Gatekeeper; the "exception applies only to the app's first run" rule ([Eclectic Light, 2024-10-01](https://eclecticlight.co/2024/10/01/living-without-notarization/)) bites only quarantined replacements. The one precondition to verify before trusting this is that Tauri's bundler does not emit `LSFileQuarantineEnabled` in the manager's Info.plist (no source states it either way). Under this reading the manager is a strictly better install path than a browser-downloaded zip and at least as good as the pkg, and the user's single Gatekeeper encounter is the manager's own first launch. Shipping the manager itself as an unsigned `.pkg` built with the `pkgbuild` step the pipeline already has (rather than a `.dmg`) keeps that single approval on the installer and leaves the installed `.app` unquarantined; this is an inference from the quarantine rules and the Tahoe test, not a documented guarantee, and is on the test list below. Homebrew is no longer an escape hatch: Homebrew 5.0.0 deprecated `--no-quarantine`, declared "Casks without codesigning are deprecated", and said it "will disable all Homebrew/homebrew-cask casks that fail Gatekeeper checks in September 2026" ([Homebrew 5.0.0](https://brew.sh/2025/11/12/homebrew-5.0.0/)).

Windows is simpler and harsher. Microsoft's guidance (updated 2026-08-17) is unambiguous: no signature yields "Windows protected your PC" with "Run anyway"; "Self-signed Certificate: Warning — Same behavior as no signature"; "SmartScreen reputation must build for each new version of your files, starting with zero reputation" and "cannot transfer from previous versions unless both were signed using the same publisher identity"; it "can take several weeks and hundreds of clean installs" with "no need (or mechanism) to manually submit a file"; and "EV certificates no longer bypass SmartScreen" ([Microsoft: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). Installer technology is irrelevant: SmartScreen keys on the file hash, so Krate's Inno `.exe` and a Tauri NSIS `-setup.exe` behave identically, and each of nine plugin releases plus each manager release starts at zero. The manager helps here too: Mark-of-the-Web is written by browsers and mail clients as the `Zone.Identifier` stream ([Outflank](https://outflank.nl/blog/2020/03/30/mark-of-the-web-from-a-red-teams-perspective/)), and a Rust HTTP download writes none, so the NSIS installer the updater launches and the plugin files the manager extracts should not trigger the download prompt (unverified for this exact case). The hard wall is **Windows 11 Smart App Control**, which "will block execution of unsigned files unless the file has a positive reputation" and whose "signature checks apply to all executable files, not just those downloaded from the Internet" ([same page](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation); [Smart App Control overview](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)): on an SAC-enforced machine neither the manager nor any Krate plugin runs, and the only remedy is the user turning SAC off. Document it as unsupported. The elevated helper will show the yellow "unknown publisher" UAC prompt every time; a per-user manager install (`currentUser`, `%LOCALAPPDATA%`) keeps that prompt out of self-update entirely ([Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/)). winget is open to unsigned `.exe` installers (its repository policies contain no code-signing clause, and an unsigned NSIS exe has been accepted in practice) ([winget policies](https://learn.microsoft.com/en-us/windows/package-manager/package/windows-package-manager-policies); [OpenScreen PR #285](https://github.com/getopenscreen/openscreen/pull/285)), and Surge XT already ships there with Inno's silent switches ([wingetly: Surge XT](https://www.wingetly.io/apps/surge-synth/surge-xt/silent-install)). Linux imposes no signing cost at all.

For completeness, two routes exist that the stated constraint rules out but a future maintainer should know about. SignPath Foundation signs OSI-licensed open-source projects for free on Windows, with the Foundation as publisher, in exchange for a public code-signing policy page, MFA, CI-built artifacts and per-release approval ([signpath.org/terms](https://signpath.org/terms)); pandoc and Ink/Stitch use it ([pandoc policy](https://pandoc.org/code-signing-policy.html)). Microsoft's Azure Artifact Signing ($9.99/month) is open to organizations in the EU but "Individual developers must be located in the United States or Canada" ([Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)). On macOS there is no foundation equivalent; the only zero-cost pattern is a volunteer's Developer ID (Surge XT appears notarized under an individual maintainer's identity ([Desktop Insights: Surge XT](https://desktopinsights.com/apps/surge-xt))), which makes that person liable and names them in every dialog.

With no platform identity, the minisign key becomes the single root of trust for the manager and all nine plugins, so its handling and the updater's version matter. Two September-2026 advisories hit the Tauri updater: CVE-2026-95624 (the webview could pass `allowDowngrades: true`) and CVE-2026-95625 (minisign covered only the binary bytes while the manifest was unsigned, allowing a forced downgrade to an older validly signed release), both fixed in updater 2.12.0 ([OSV CVE-2026-95624](https://osv.dev/vulnerability/CVE-2026-95624); [OSV GHSA-j38x-g3m3-95fr](https://osv.dev/vulnerability/GHSA-j38x-g3m3-95fr); [updater 2.12.0 notes](https://v2.tauri.app/release/updater/v2.12.0/)). The required configuration is updater **≥ 2.14.1**, `allowDowngrades` left at its default `false`, and `requireSignedVersion: true` so the version in the signature's trusted comment must match the announced version ([config.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/config.rs)). Tauri's docs add the operational warning: "Losing the private key means you cannot publish updates to existing installs" ([Tauri updater plugin](https://v2.tauri.app/plugin/updater/)). This covers MITM, a hijacked Pages site, a tampered release asset and replay of an old version; it does not cover a leaked CI secret or a compromised GitHub account that both edits the feed and re-signs, and it buys nothing against Gatekeeper or SmartScreen.

## Extend versions.json additively, add archives and signatures, split out two workflows

The baseline is friendlier than it looks. `release.yml` is a manual, one-plugin-per-run workflow that tags `<plugin>/vX.Y.Z`, uploads an Inno `.exe`, an unsigned `.pkg` and a `.tar.gz`, and regenerates `versions.json` from local git tags with `download_url` set to the plugin's homepage and `release_notes` always `""` (`F:\projects\iterum\.github\workflows\release.yml`). The shipped parser in all nine plugins requires only that `plugins.<Name>.version` is a string, reads `download_url` and `release_notes` if present, **never reads `schema_version`**, and treats any parse exception as "no update" (`F:\projects\iterum\plugins\shared\src\update\update_checker.cpp` lines 221-262); every plugin hard-codes `https://rolandzwaga.github.io/krate-audio/versions.json` (e.g. `plugins/disrumpo/src/update/disrumpo_update_config.h` line 12). So a single `versions.json` can move to `schema_version: 2` with new keys placed *beside* the three existing ones, and nothing in the field breaks; the only forbidden moves are removing, retyping or nesting those three keys, or putting markdown into `release_notes`, which nine editors render inline. A guard test in `plugins/shared/tests` that feeds a v2 document to `parseResponse` and asserts the v1 fields still come back is cheap and should land with the schema.

The v2 vocabulary should borrow Tauri's `platforms.{os}-{arch}.{url,signature}` keys so the manager's self-update file and the plugin feed share one dialect, plus `size`, `min_os`, `channel` and `release_notes_url` from Sparkle's appcast and a per-asset `sha256` from Scoop/winget ([Tauri updater plugin](https://v2.tauri.app/plugin/updater/); [Sparkle publishing](https://sparkle-project.org/documentation/publishing/); [Scoop manifests](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifests); [winget manifest](https://learn.microsoft.com/fi-fi/windows/package-manager/package/manifest)). Each plugin entry gains `tag`, `pub_date`, `channel`, `notes_markdown`, a `platforms` map whose entries carry the plain archive as the primary `url` and the legacy installer under a nested `installer` object, and an `install` block (`vst3_bundle`, `au_component`, `presets_subdir`, `windows_uninstall_key`, `macos_pkg_id`) that lets the manager find and remove pre-manager installs. Prereleases go under a `channel: "beta"` sibling, not into `version`, because the v1 parser upgrades on any higher SemVer. The Tauri updater cannot read a nested per-plugin object: its static JSON must have `version` and `platforms` at the top level and "Tauri validates the whole file before checking the version, so every platform entry must be complete" ([Tauri updater plugin](https://v2.tauri.app/plugin/updater/)), so the manager's own update file is a separate `manager/latest.json` that tauri-action emits and `versions.json` merely points to. One file cannot satisfy both parsers; do not try.

Two URL rules follow from GitHub's documented behaviour. The feed must never contain `/releases/latest/download/...`: "The latest release is the most recent non-prerelease, non-draft release, sorted by the created_at attribute" ([GitHub REST: Releases](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28)), and in a monorepo that is whichever plugin shipped last, so a Vorago release would silently retarget an Iterum link; use per-tag `browser_download_url` values verbatim and consider `make_latest: false` on plugin releases. And the manager must never call `api.github.com`: unauthenticated requests are capped at **60 per hour per originating IP** ([GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)), which one studio behind NAT would exhaust. Keep the JSON on GitHub Pages (soft 100 GB/month, 1 GB site, observed `Cache-Control: max-age=600` so the feed is at most about ten minutes stale) and every binary on Releases ("no limit on the total size of a release, nor bandwidth usage", 2 GiB per file) ([GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits); [About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). Give the Tauri updater two endpoints, the Pages URL first and the per-tag release asset second; it fails over only on a non-2XX status.

| Artifact per plugin release | Today | Add in v2 |
|---|---|---|
| Windows | `<Name>-<ver>-Windows-x64.exe` (Inno) | `<Name>-<ver>-Windows-x64.zip` (`<Name>.vst3/` folder + `presets/` + `CHANGELOG.txt`) |
| macOS | `<Name>-<ver>-macOS.pkg` (unsigned, `pkgbuild`) | `<Name>-<ver>-macOS.zip` made with `ditto -c -k --keepParent` (never `zip -r`: bundle symlinks and exec bits must survive) |
| Linux | `<Name>-<ver>-Linux-x64.tar.gz` (already the right layout) | unchanged; add a `format: "tar.gz"` entry |
| All | — | `SHA256SUMS`, one `.minisig` per asset, `release.json` (per-release manifest), build-provenance attestation |

The Windows and macOS jobs already stage exactly these files, so the archive steps are a few lines in existing jobs ([ditto guidance](https://flaviocopes.com/courses/ship-macos-apps/create-a-zip-with-ditto/)). Signing in CI is one `rsign2`/`minisign` call per asset; the manager verifies with the zero-dependency `minisign-verify` crate the Tauri updater itself uses ([docs.rs minisign-verify](https://docs.rs/minisign-verify)), after comparing `Content-Length` to `size` and the streamed SHA-256 to the feed. If `tauri signer` keys prove minisign-compatible (a secondary source says so; verify once with `rsign2`), one `TAURI_SIGNING_PRIVATE_KEY` signs both the manager bundles and the plugin archives, and the manager's self-update and plugin verification share a public key. GitHub artifact attestations (`actions/attest-build-provenance`, free for public repos, SLSA Build Level 2, verifiable with `gh attestation verify`) belong in the `release` job as a human-facing provenance layer, but not inside the manager, where a Sigstore trusted-root refresh would add a network dependency for a check minisign already provides ([GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations); [gh attestation verify](https://cli.github.com/manual/gh_attestation_verify)).

The pipeline splits into three workflows. `release.yml` keeps its job but gains the archive, hash, signature and `release.json` steps and then calls the feed. `release-manager.yml` runs `tauri-apps/tauri-action` on a `create-release` job plus a matrix of `windows-latest`, `macos-latest` with `--target universal-apple-darwin`, and `ubuntu-22.04` with the apt line `libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf xdg-utils`, with `TAURI_SIGNING_PRIVATE_KEY` and its password as secrets; the action uploads bundles, `.sig` files and `latest.json`, maps a universal build to both `darwin-aarch64` and `darwin-x86_64`, and must be given `tagName` (not only `releaseId`) or its `latest.json` will point at `releases/latest/download/` ([tauri-action README](https://github.com/tauri-apps/tauri-action); [Tauri GitHub pipeline](https://v2.tauri.app/distribute/pipelines/github/)). `feed.yml` (`workflow_call` + `workflow_dispatch`) rebuilds `versions.json` idempotently from `gh release list` and each release's `release.json` rather than from local tags (so it needs no `fetch-depth: 0` and can be re-run by hand), copies `manager/latest.json`, and deploys with `peaceiris/actions-gh-pages@v4` and `keep_files: true`; it spends about twenty of the 1,000 hourly `GITHUB_TOKEN` requests. Per project rule the generator is Node, replacing the inline Python that builds the Pages index today (`F:\projects\iterum\CLAUDE.md`). All of this is free: "The use of standard GitHub-hosted runners is free: In public repositories", macOS included ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). One deadline is already running: the `ubuntu-22.04` runner image entered deprecation on **2026-09-17**, will be "fully unsupported by April 17th, 2027" with brownouts from March 23, 2027, and workflows using the label "will be terminated with an error" ([actions/runner-images #14254](https://github.com/actions/runner-images/issues/14254)). Since the AppImage and the plugins' glibc floor (2.35 on 22.04) depend on the build host, plan now to build the Linux legs in a 22.04 container on a newer runner, as the Tabularis team did, and record each Linux build's minimum glibc in `release.json`. The macOS leg of `release.yml` also needs the ad-hoc codesign step from the previous section; it is the one change on this list that is mandatory for Apple Silicon users regardless of whether the manager ever ships.

## Copy Audio Damage's single screen, not Native Access's daemon

Prior art converges on a small set of behaviours that users reward and a longer list they punish. A January 2026 KVR thread on the worst plugin managers singles out Audio Damage as the best because "installs are instant, with a single screen to pick a version and install", praises Arturia, Spitfire and Waves Central as painless, and names the recurring sins: installing everything, no download queue, downloads that stall or need manual resumes, forced full reinstalls, updates "with identical version numbers", and path settings that are hidden or unchangeable ([KVR thread](https://www.kvraudio.com/forum/viewtopic.php?p=9182325)). Cherry Audio Sync's feature list reads like a specification for Krate v1: status of all products in one place, an Updates tab showing "only products with available updates", "update products one at a time or all at once", formats and a custom folder chosen once in Preferences, and "uninstall or reinstall a product without deleting your user presets" ([Cherry Audio: Sync](https://cherryaudio.com/products/sync)). VS Code's extension view supplies the general-software vocabulary: a state button that flips Install → Manage, an `@updates` filter, "Update All", CHANGELOG on the details page, and "Install Another Version" for rollback ([VS Code: Extension Marketplace](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace)). Because Krate has no accounts, licences, trials or stores, each card collapses to installed version, available version, one action (Install / Update / Reinstall / Remove) and release notes. Rollback is worth a button from day one, since no updater library offers it and Tauri's downgrade path needs a dynamic server: keep the previous artifact in the app data directory and re-feed it through the same minisign check. No open-source project does the whole job; the closest, PluginVault, is a Tauri 2 + Rust scanner that reads `moduleinfo.json`, `Info.plist` and PE version info but has one star and four commits ([GitHub: GalAzu/pluginvault](https://github.com/GalAzu/pluginvault)), so it is study material, while yabridgectl's `add | status | sync` reconcile model (4.2k stars) is the cleanest architectural reference ([GitHub: yabridge](https://github.com/robbert-vdh/yabridge)). Krate's structural advantage over every scanner that misdetects versions is that it controls the bundles and can guarantee `moduleinfo.json` is present and consistent.

Several load-bearing claims in this report rest on mechanism plus community reports rather than vendor documentation, and each resolves with a short experiment. Running these before committing the architecture is cheaper than discovering them from support tickets.

| Open question | Why it matters | Test |
|---|---|---|
| Does Tauri's bundler set `LSFileQuarantineEnabled` in Info.plist? | Decides whether manager-written plug-ins and update bundles are unquarantined | Inspect the built `.app/Contents/Info.plist`; `xattr -l` on an installed bundle |
| Does "Open Anyway" still appear for an ad-hoc-signed, quarantined app on Tahoe? | Sets the first-launch instructions | 10 minutes on a Tahoe VM |
| Does an unsigned manager `.pkg` run via Installer.app leave the `.app` unquarantined, and does `sudo installer -pkg` skip Gatekeeper? | Chooses pkg vs dmg for the manager download | Quarantined copy of a Krate pkg, then `xattr -l` on the payload |
| Which Windows DAWs scan `%LOCALAPPDATA%\Programs\Common\VST3`? | Decides whether per-user can ever be the Windows default | REAPER, Ableton, FL Studio, Cubase, Studio One, Bitwig with a test bundle |
| Does SmartScreen fire on an exe written by `reqwest` and launched via `ShellExecute`? | Decides whether Windows self-update is silent | Download the unsigned NSIS exe in-app, observe |
| Are `tauri signer` keys minisign-compatible? | One key or two for manager and plugins | Sign a file with `tauri signer sign`, verify with `rsign2` |
| Does an ad-hoc Tauri `.app` replace itself cleanly on Sequoia/Tahoe? | Confirms unsigned self-update end to end | Two signed builds, run the updater, `codesign --verify --deep --strict` after |
| Which `moduleinfo.json` `Version` should the manager trust? | Membrum shows `0.8.0` top-level vs `0.12.2.1` per class | Fix the SDK build to emit both from `version.json`; parse JSON5 |

## Conclusion

The decisive insight is that under a never-sign policy the usual trust ordering inverts: an installer downloaded in a browser is the *worst* path a Krate user can take (quarantined on macOS, SmartScreen on Windows, no uninstaller for a `.pkg`), and a manager that fetches bytes with its own HTTP client and writes them itself is the best, because both Gatekeeper and SmartScreen key on provenance marks that only browsers write. That makes the manager less a convenience than the primary distribution channel, and it means the plan's first investments should be the mundane ones: the ad-hoc codesign step in CI, the quarantine and SmartScreen experiments in the table above, and a `moduleinfo.json` that agrees with `version.json`. Tauri is the right vehicle not because it is small or fashionable but because its updater's threat model (a key you own, a manifest you host) is the only one on offer that never asks Apple or Microsoft for permission.

Two things should be revisited rather than decided now. Wails v3's updater, three days old at research time, could become the no-Rust alternative if production reports confirm it installs unsigned macOS bundles; check again in six months. And the Windows per-user VST3 folder is the one place where Steinberg's spec and DAW reality diverge; if the per-DAW test comes back green, the Windows default can move to per-user and the elevated helper becomes an opt-in on every platform, which would make Krate Manager the first audio plugin manager with no privileged code path at all.
